## 发现与修复

### 暂停后翻页，标题和指标保持空白

在月报和年报中均复现：暂停播放后点击下一章，进度条切换，但标题和指标
停在透明的第一帧。恢复播放后文字才出现。

`CycleReportPlayer.next()` 和 `previous()` 将章节时间清零，而暂停状态不推进
时间。修复为暂停浏览时直接展示目标章节的完成帧；向前返回时直接进入上一章。
播放中的章节重播、临时按住和恢复播放保留原有语义。

新增三个回归测试覆盖暂停前后翻页、从末章返回、播放及临时按住时的导航。
45 项报告测试实际运行并通过，`check:ios`、`check:version` 通过；模拟器测试
构建和已签名真机构建均成功。

Debug 真机已复验暂停后下一章的标题、指标和图形正常出现；20:43 补齐上一章
和末章返回操作，内容均立即完整显示，播放保持暂停。

### Watch 贪睡未使 iPhone 停止响铃

20:12，一分钟测试闹钟在 iPhone 上显示 DoneAt 系统闹钟界面。用户在配对的
Apple Watch 点贪睡后，明确反馈 iPhone 仍继续响。该跨设备用例未通过，
不能据此计为九分钟贪睡成功。

事后核对操作记录发现，验证人员向测试按钮进行了两次坐标点击：第一次之后
按钮布局位置改变，第二次为更正重试。按钮没有可见的预约成功提示，因此
无法确认第一次未命中，也无法排除两个测试闹钟同时存在。当前 Debug 入口
每次点击生成新的 UUID。这使本次用例无法单独证明跨设备贪睡存在产品缺陷；
下次必须先确认没有残留闹钟，只预约一个，再验证手机与 Watch 的停止/贪睡。

当前实现使用 AlarmKit 原生 `.countdown` 次按钮和 540 秒 `postAlert`，
与 [Apple 的贪睡配置说明](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit)
一致。Watch App 没有独立预约闹钟或自行处理贪睡；仍需实际状态证据区分
重复预约、跨设备同步和系统行为，不能直接归因于 Apple 或 DoneAt。

响铃期间 iPhone 镜像断开，无法远程操作手机的系统闹钟。20:16 的只读截图
显示手机已回到 DoneAt 设置，班次闹钟为关闭；验证人员没有执行这一变化，
因此未将其记为程序自动停止或自动关闭。此后没有再安排测试闹钟。

随后再次读取偏好，`shiftAlarmSettings.isEnabled` 仍为 `true`，与测试前的
`false` 不同，提前量保持不变。设置摘要还取决于 Plus 权益，单凭“关闭”字样
不能证明开关已恢复或系统预约已清空。同期再次比对存档，业务内容仍完全一致，
仅导出时间变化；隐藏收入
和 CloudKit 同步开关保留原值，没有持久化测试 Plus 授权。

20:33 镜像恢复后，在临时测试权益下通过真实开关关闭班次闹钟。重新读取偏好，
全部闹钟设置与测试前一致（`isEnabled == false`，提前量未变）；预约列表随开关
消失。20:52 从 TestFlight 覆盖恢复原 3.2.1（202），普通启动后真实权益、记录、
隐藏收入和关闭的闹钟均经 UI 与本机数据核对。

## 性能证据的边界

使用 Instruments 定向附加 DoneAt。31 秒 Animation Hitches 记录包含一次
52 ms 潜在交互延迟；随后 120.94 秒 SwiftUI 记录未检出 hangs/hitches。
后者覆盖报告和普通页面操作，并非连续 120 秒播放同一报告。

iPhone 镜像使用无线虚拟显示，导出的显示帧计数表没有可用数据。
上述结果不证明物理屏幕持续 120 fps。触感强度与实体屏幕帧率仍需现场验收。

## 记录页月历滚动

用户报告真机记录页、尤其月历上下滚动顿挫。使用同一台真机、当前记录与
Debug 构建，录制十月月历上下滚动。由于附加当前 Debug 进程失败，改由
Instruments 启动 App；采样结束返回主屏对应工具的正常 `exit(0)`，没有
将此算为 App 崩溃。

滚动发生在采样的 41.5–55 秒内。该 13.5 秒窗口没有检出的 hangs/hitches，
但有 11,028 次 SwiftUI 更新；位置变换向日期浮层 anchor 传递了 2,976 次更新，
anchor 又向懒网格的 preference 传递了 1,296 次，期间没有选中日期。
启动阶段另有 1.635 秒主线程停顿，主要为 Swift 泛型元数据初始化，未计为
滚动卡顿证据。

优化只为选中日期登记浮层 anchor，保留按钮的结构和命中区域；未选中时
不创建浮层 GeometryReader。同样应用于周视图，并移除时间分配条未消费的
anchor。暂未更换月历的懒网格，以便先验证这处确定的无用更新。

真机与模拟器构建通过；两项现有画布交互测试实际运行并通过（浮层边界、
选中范围），`check:ios`、`check:version` 通过。优化后真机已验证月历换日选择、
滚动时浮层跟随、打开日详情再返回，以及周视图选中浮层，均正常。

优化后的同组三批滚动发生在采样的 42.057–50.544 秒窗口（含尾部静置）：
完整查询 `AnchorWriter<CGRect, RecordsSelectionAnchorKey>` 的更新来源，匹配数为
零，确认未选中时不再跟踪日期浮层位置。

| 指标 | 优化前 | 优化后 |
|---|---:|---:|
| 分析窗口 | 13.5 秒 | 8.487 秒 |
| 采样 CPU 时间 | 251 ms | 325 ms |
| SwiftUI 更新数 | 11,028 | 11,867 |
| 位置变换 → 日期浮层 anchor | 2,976 | 0 |
| 检出的 hangs / hitches | 0 / 0 | 0 / 0 |

两次远程输入用时和渲染帧数不同，表中 CPU 与总更新数不能用来计算性能提升。
已验证的是无用 anchor 更新被移除；本次没有抓到滚动 hitch，尚未证明用户
感受到的顿挫完全消失，也不能据此宣称达到物理 120 fps。
