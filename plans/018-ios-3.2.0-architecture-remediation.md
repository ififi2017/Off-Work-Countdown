## 2. 数据与应用结构整改

### P1 · 先减少重复写入和无关刷新

把“设置赋值即执行完整持久化”改成明确的提交操作。

- [ ] 设置页面持有编辑草稿，通过 `applyPreferences`、`applyScheduleChange` 等具体入口提交。一次操作涉及的偏好、排班记录及 Focus 联动纳入同一个批次。
- [ ] 复用现有 `withBatchedWrites`，补齐业务内容相等检查。没有变化时，不生成新编辑戳、不更新 outbox、不写盘、不广播变化。
- [ ] 普通提交完成一次归档保存，再通知下游；消除多个 `didSet` 对同一操作的重复保存。
- [ ] 将完整档案的编码、校验和原子写入移入独立串行持久化执行器。保留现有文件格式、损坏保护和导入校验。
- [ ] 写入请求携带不可变快照及提交序号，按序执行；旧写入完成不能覆盖较新状态。提供可等待的持久化结果与 `flush` 边界。
- [ ] 普通编辑保留即时内存反馈，写入失败保留待保存状态并明确提示；导入、恢复和清库继续采用“候选数据成功落盘后才替换当前状态”。导出、远端确认及系统入口成功回执必须等待相应提交完成。

将通用 `revision` 拆成少量明确的变更域，并由消费者比较自己的实际输入：

- [ ] Records 查询只依赖影响记录结果的内容。
- [ ] Life 保留现有后台计算和缓存，缓存键移出 Store，避免无关变化反复构造历史数组键。
- [ ] 同步元数据变化不触发记录重算。
- [ ] 主题变化不触发班次重算、通知重排或 Watch 班次重发。

### P2 · 拆分真正拥有状态和行为的对象

最终依赖方向为：**场景界面 → 功能状态／动作 → 规则和记录服务**。系统入口通过同一功能动作执行，不依赖页面是否已经出现。

| 边界 | 负责内容 |
| --- | --- |
| `AppRuntime` | 进程级依赖装配、共享数据实例；不承接业务方法转发 |
| `SceneState` | 当前标签、导航路径、弹窗及编辑草稿，每个场景独立 |
| `PreferencesStore` | 已提交偏好、读取旧设置、设置提交入口 |
| `ShiftSessionStore` | 当前班次会话、开始／停止及班次变更联动 |
| `FocusStore` | 专注计划和运行生命周期，复用现有纯模型 |
| `RecordsQueries`、`LifeSummaryModel` | 查询、展示投影、缓存及异步准备 |
| `ServiceCoordinator` | 启动、前后台对账、通知、Widget、Live Activity 和 Watch 发布 |

实施约束：

- [ ] 按导航状态、Focus、Records／Life、班次与偏好的顺序迁出旧 Store；迁移期间允许临时兼容入口，每个入口随调用方迁移删除。
- [ ] 收口时，业务 View 不再接收整个 `OffWorkStore`，只接收所需功能对象或值模型。
- [ ] `AppRuntime` 保留必要的进程级共享实例，供 App Intents 与 App 使用；导航和草稿不进入共享实例。
- [ ] `RootView` 只装配界面并转交场景生命周期事件。现有服务内部的取消、串行化和代际保护继续保留。
- [ ] JavaScriptCore 上下文继续保持现有隔离；后台计算只接收可安全传递的值，不跨线程搬运上下文。
- [ ] 复用已有 `RecordIncomingValue`，通过穷举分支统一取得身份、编辑版本和冲突排序信息，移除运行时类型判断中的 `nil`／`0` 静默回退。保留现有删除标记、冲突副本和同步代际机制。

### P4 · iOS 27 与 iPhone Duo 基础适配

> 2026-09-19 最新范围：用户明确将 Duo 专属适配移至下一版本，依赖 iOS 27.1 SDK，不再阻塞 3.2.0。常规 iPhone／iPad 与 iOS 26／27 兼容验收仍需完成。

布局依据改为**当前场景的可用空间、尺寸类别和内容需求**，消除“只有 iPad 才能进入宽布局”的条件。

- [ ] 复用现有窄屏与宽屏内容，通过原生导航容器组织。窗口变化、折叠展开和旋转时，保留所选日期、导航位置、编辑草稿和运行中的计时。
- [ ] 将横屏倒计时改为场景内部的展示状态，避免额外 `.alert` 级窗口承担正常布局切换。
- [ ] iOS 27 路径采用系统适应能力；iOS 26 必须保留的方向兼容代码封装在独立适配层，只服务既有方向行为，不参与 Duo 布局判断。
- [ ] 工具栏按主次处理空间不足：主要操作保持可达，次要操作进入系统溢出区域。新增 API 按实际版本门控，保留 iOS 26 路径。
- [ ] 对受 SDK 更新影响的 `@State` 初始化和 builder 编译问题做定点迁移；不进行无收益的全项目语法替换。

iOS 27 的可调整窗口能力应以场景布局为基础，包括 iPhone Mirroring 的尺寸变化。[Apple 平台说明](https://developer.apple.com/videos/play/wwdc2026/102/)

Duo 的基础适配覆盖外屏、展开内屏和部分折叠：

- [ ] 标准导航、列表和弹窗优先使用系统适配。
- [ ] 倒计时主信息与操作区采用可分离布局；记录和 Focus 画布根据实际可用区域调整，保证主要时间及关键按钮不跨遮挡区域。
- [ ] 自定义布局使用系统提供的 reserved regions，禁止硬编码型号、屏幕像素或折痕位置。
- [ ] `ArrangementView` 按 **iOS 27.1** 可用性采用，仅用于适合分区的主内容与辅助内容；26／27.0 保留普通自适应容器。[Apple Duo 适配说明](https://developer.apple.com/videos/play/tech-talks/111463/)

Apple 参考检索日期：2026-09-12。实现时以相应 SDK 的实际声明及可编译验证为准；本地 skill 不是 CI、构建或验收的依赖。

## 5. 追加范围（2026-09-13）

### P7 · macOS 应用图标改用 Icon Composer

iPhone、iPad 与 Apple Watch 已改用 `assets/brand/AppIcon.icon`（PR #182）。macOS 仍使用 `src-tauri/icons/icon.icns`，这是 2026-08-29 从扁平 SVG 生成的位图，在 macOS 26 上没有 Liquid Glass 层次。

本机实测（2026-09-13，Xcode 26.6）：`actool --platform macosx` 编译同一份 `AppIcon.icon`，得到 `Assets.car`、`AppIcon.icns` 与 `CFBundleIconName = AppIcon`，渲染结果与 Icon Composer 一致；但生成的 `.icns` 最大只有 256 px，不能替代现有 1024 px 的 `icon.icns`。

- [x] **Mac App Store 渠道先行。** 在 `tauri.macappstore.conf.json` 已有的 `beforeBundleCommand`（`scripts/build-macos-widget.sh`）或独立脚本中，用 `actool` 从 `assets/brand/AppIcon.icon` 生成 `Assets.car`，经 `bundle.macOS.files` 放入 `Contents/Resources`，并写入 `CFBundleIconName`。现有 1024 px `icon.icns` 保留，作为 macOS 26 之前系统的回退。
- [ ] **GitHub 渠道。** `release-desktop.yml` 在 `macos-latest` 上通过 `tauri-action` 构建；先确认 runner 的 Xcode 能编译 `.icon`，再接入同一脚本。不能编译时本渠道暂保留 `icon.icns`，并在此记录原因。`src-tauri/Info.plist` 为各 macOS 渠道共用，`CFBundleIconName` 必须与 `Assets.car` 同时出现，不能只加其中之一。
- [x] 与 iOS 相同，不使用软链接；生成的 `Assets.car` 属于构建产物，不提交。Windows、Web 与菜单栏标记图不在本项范围内。
- [ ] 验证：macOS 26 的 Finder、Dock、启动台显示新图标；最低支持版本（Mac App Store 13.0、GitHub 11.3）回退正常；`pack:macappstore` 与签名检查不回退。只在本机打包，不上传。
- [x] iOS 实时活动里的 `BrandIcon` 小图标保持现有扁平图，不改用新图标渲染（2026-09-13 用户决定）。

**实施（2026-09-13 进行中）**：

- `scripts/generate-macos-icon.mjs` 在 macOS 上用 `actool` 把 `assets/brand/AppIcon.icon` 编译到 `src-tauri/target/macos-icon/Assets.car`，并校验 `CFBundleIconName` 为 `AppIcon`；Xcode 低于 26 编译不了 `.icon` 时，改用现有 `icon.icns` 展开成传统图标集编译并打印原因（回退路径已在本机单独验证）。非 macOS 跳过。
- `scripts/build-desktop.mjs` 在生成 lproj 之后调用它，GitHub 与 Mac App Store 两个渠道共用；`tauri.macos.conf.json`（仅 macOS 构建合并）的 `bundle.macOS.files` 放入 `Resources/Assets.car`；`src-tauri/Info.plist` 增加 `CFBundleIconName`。

### P8 · 扩展排班：班次类型、预制规则与自由日历（用户反馈）

**来源**：2026-09-12 一位用户在社交平台评论，说自己的排班不固定、没有规律，询问能否自定义上班日。作者回复的方案是：在程序里放一个月历，提前设置本月和下个月的排班；再往后的月份如果没有人工设置，就自动沿用上个月的排班。用户表示可以。作者当时说大概在“下下个版本”更新。（仓库不记录该用户的账号。）

**现状**：

- `lib/countdown.ts` 的排班模式只有固定星期（classic）、单双周（alternating）、轮班（rotation）和手动（off），没有按具体日期指定，也没有班次类型。
- iOS 已有 `CalendarException`（某天休息或补班，记录页可标记）和 `DayOverride`（某天实际时段或请假）。它们作用于记录的逐日解析，用于记录、汇总和周期总结通知；实时倒计时只认当天一次性的「今天上班」标记。两者都不支持按月批量预设，也没有“沿用上个月”的规则。

**2026-09-13 用户确认的产品方向**：

- **基础排班（默认）**：一周 7 天中自选工作日，默认都是白班。
- **扩展排班**：把单双休、轮班轮休和完全自由的日历合并成一个扩展功能。
  - 进入后先展示一个月的日历。
  - 用户配置班次类型：可自定义名称和时间段（例如早班、晚班、夜班）。
  - 可以快速套用预制规则（单双休、轮班轮休），为规则周期内的每一天指定班次类型，由程序自动生成班次日历。
  - 也可以不用规则，自由指定日历里每一天是什么班次，并可以提前填好下一个月。
- **再往后的月份**：没有人工设置时，按**日期号**直接复制上个月，不按星期规律推算，因为这类排班可能完全没有规律；用户随时可以再调整。
- **平台**：作为 iOS 独立的改进，不要求 Web／Desktop 同步提供。

**规则位置**：用户决定 iOS 的核心规则回到 Swift，iOS 文案回到 iOS 工程内按 Swift 规范存放，理由是两端功能越来越分化，维护成本上升。这与 `AGENTS.md` 当前“规则不移植到 Swift”的规定相反，门槛、契约与迁移顺序见 [019](019-ios-native-rules-and-localization.md)。P8 的规则实现依赖 019 的排班入口先迁到 Swift，不在 TypeScript bundle 里新增一套只有 iOS 使用的排班模式。

**2026-09-13 用户确认的细节**：

1. **缺失日期**：按日期号复制时，源月份没有的日期（例如 2 月复制到 3 月的 29–31 日）视为休息。
2. **推算与“预定”**：
   - 人生视图和收入推测对未来工作年限的推算，只用**本月**的班表按日期号重复，不逐月生成独立班表。
   - **下个月**的班表作为“预定”暂存，自然时间进入下个月时自动应用为本月班表。
   - “接下来”区域需要针对这一逻辑优化，区分已生效的本月班次与尚未生效的预定班次（现有实现见 `UpcomingTimelineView`、`RestDayUpcomingView`、`ShiftSetupTimelineView`）。
   - 用户可以补填本月以前的班次，用来改进排班统计结果。
3. **班次类型**：
   - 名称与时间段可自定义，允许跨午夜。
   - 有一个“中途休息”开关，开启后可以设置休息时间段。扩展排班内不出现“午休”字样。
   - 颜色自动生成，用户可以修改。
   - “休息”是一种班次类型，但不会触发上班倒计时。
4. **手动修改优先**：用户手动改过的日子，之后再改规则也不覆盖；用户可以把某天恢复为按规则计算。
5. **冲突**：仓库没有内置的节假日或调休数据（`CalendarException` 的内置来源从未写入），唯一的例外来自用户操作。用户手动开始倒计时等行为按人工修改记录处理，同样优先于规则，不存在其他冲突。
6. **权益与版本**：不属于 Plus。发布版本未定，默认不阻塞 P6 的 3.2.0 收口。

设计要点：

- **生成与内置**：新增生成脚本，锁定来源版本，产出按国家／地区、按年份的精简 JSON（日期、休息或调休上班、本地化名称），记录 `datasetVersion` 与每个地区的 `coveredThroughYear`。生成结果随仓库提交，Xcode Cloud 构建不依赖 PyPI 或网络；检查脚本校验内置数据与锁定版本一致。
- **年份覆盖的区别**：固定日期与按农历或规则推算的节日可以算出未来年份；依赖政府公告的安排（中国调休、部分国家的补休）只有公告后才有。中国大陆按公告数据记录覆盖范围，不自行推测调休；其他地区记录上游规则生成的年份范围，不能将未来规则计算结果称为已获政府公告确认。
- **兜底提示**：所选节假日模板在排班或“接下来”涉及到未覆盖的年份时，按普通排班计算，并提示用户“节假日数据只到某年，请检查 App 更新”；年底前（例如 12 月）若下一年仍未覆盖，在排班设置中提前提示。App 不联网拉取数据。
- **优先级**：用户手动修改优先于节假日模板，节假日模板优先于排班规则。
- **默认与选择（2026-09-13 用户确认）**：按系统地区默认勾选对应的节假日模板；用户可以改选其他国家或地区，也可以直接关闭。

**实施记录（2026-09-16 · P8-b 解析规则）**：

- **解析链**（`Native/Models/ExtendedScheduleRules.swift`）：手动指定的某天 > 周期规则 > 按日期号沿用更早的月份；三层都没有结论就是休息。节假日模板本应排在手动与规则之间，这一批没有实现——内置数据还没有生成（见上方「节假日模板」），留到那批一起落地，代码里标明了它的位置。
- **沿用上月**：目标月份一天都没有人工设置时，按日期号复制最近一个有人工设置的月份；源月份没有的日期（2 月复制到 3 月的 29–31 日）算休息。用户在某个月动过哪怕一天，这个月就算他自己排的，其余日子是休息，不会把两个月混在一起。
  - **与计划原文的差别**：计划写的是推算未来「只用本月的班表按日期号重复」，实现取的是「目标月份之前最近一个有人工设置的月份」。用户没有预排未来月份时两者结果相同；预排了下个月时，实现会让再往后的月份沿用那个预排月份，而不是回头沿用本月。如果更希望严格按本月重复，P8-c 改回即可。
- **接入方式**：解析结果是与现有规则相同的「上班时段 + 中途休息 + 是否上班」三元组，交给 `CivilZone` 原有的班次、下一班、跨夜与区间展开逻辑，不新增第二套排班算法。没有扩展排班（未启用或为空）时每条路径与之前逐字一致，共享差分 fixture 不受影响。
