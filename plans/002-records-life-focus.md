## 出发点：这个 App 现在没有记忆，但「推算」不是缺陷

当前应用保存排班、薪资与偏好，却没有跨日的历史记录：

- 「本周工作天数 / 小时」来自当前排班规则的推算，不是考勤。
- 应用没有保存用户何时第一次打开计时页、何时开始或停止一次倒计时。
- 用户几天不打开应用，就不会留下任何使用事件。

这不意味着我们应该把应用打开时间补成「真实上下班时间」。

有人会提前到公司后打开应用等待计时，有人下午无聊才来看一眼，也有人几天都不会打开。
应用处于前台，只能证明用户看过这个工具，不能证明他正在工作；倒计时结束，也不能证明
用户已经离开公司。早来和晚走更不必然改变工资。

因此，**用户主动设置的排班与职业阶段，才是工作如何占据生活的稳定底图**。应用事件可以
作为补充观察，帮助用户回望这一天发生了什么，但不能冒充考勤、薪资依据或关于实际工时的
铁证。**需要修正时，修正权在用户手里**——用户可以直接编辑某一天，而不是让应用去猜。

## 我们为什么要做「记录」

倒计时回答的是今天：「还要多久下班？」

记录与人生视图回答的是更长的问题：

- 工作在一天、一个月、一年里占去了多少时间？
- 除去工作和睡眠，真正属于自己的清醒时间还有多少？
- 如果按现在的节奏走到退休，职业生涯会有多少时间交给工作？
- 工作之外，还有哪些时间值得被看见、被保护、被认真安排？

它的价值不在于复刻一份精确考勤表，而在于把抽象的年月变成可感知、可触摸的比例。我们希望
用户看清工作在生命里的位置，从而更有意识地维护 work-life balance，而不是被一套并不可靠的
「实际工时」数字审判。

### 产品价值观

1. **排班是底图，不是次等数据。** 对多数固定工作的用户，约定好的班次比应用在线时间更能
   表达工作长期占据了多少生活。
2. **观察是线索，不是事实。** 打开应用、启动计时等事件可以丰富回顾，但必须以「观察到」
   来表达，并且只用于解释某一天，不进入任何聚合指标。
3. **修正权在用户，不在算法。** 应用永远不推断用户是否迟到、早退或真的加班；用户可以直接
   把某一天改成他说的样子，也可以清空回到排班默认。
4. **允许近似，但必须诚实。** 职业生涯尺度本来就是推演。可以使用退休年龄、平均睡眠和历史
   排班，但要把假设说清楚，并允许用户修改。
5. **时间属于用户，不属于生产力评分。** 非工作时间不是等待被填满的空白，不提供道德化提醒、
   同龄人排名或用红色制造焦虑。
6. **这不是一款记账软件。** 收入永远由排班与薪资设置决定：观察不改写收入，当日覆盖也不
   改写收入。原因见「收入口径」一节。

### 明确不做什么

- 不做考勤、雇员监控或定位追踪。
- 不把前台停留、倒计时会话或通知交互累计成「真实工时」。
- 不把记录包装成工资结算、劳动争议或绩效评估的证据。
- 不要求用户重建每一份工作的逐日历史，才允许查看人生视图。
- 不因为某天没有打开应用，就在时间轴上制造「未知的一天」或历史空洞。
- 不用精确到分钟的幻觉掩盖数据本身只是排班推算。
- 不做「人生只剩多少周」式的寿命倒计时——人生视图的右边界是退休，不是死亡。

## 数据与平台边界

### Apple 平台与 CloudKit

CloudKit private database 适合 Apple 设备之间的私有同步，但不是 Android 的同步后端，也不应被
描述成跨平台云账户。首版边界是：

- iPhone / iPad：同一 Apple Account 下可同步。
- **Mac**：不写原生 Mac 客户端。iPad 版本身可在 Apple Silicon Mac 上运行，记录能力随之覆盖
  Mac；`src-tauri` 的桌面端继续与 Windows 一并更新，但更新频率低于 iOS，且**不参与记录**——
  它不共享 SwiftData，让它读同一份数据需要先回答「原生重写还是读 JSON」，不在本文件范围内。
- 没有登录 iCloud、iCloud Drive 关闭、离线或额度不足：本地记录仍可创建、查看和修改。
- Android：首发不承诺 CloudKit 同步，版本化 JSON 是一等迁移通道。
- Web：只有在隐私、付费和使用场景明确后再决定，不为未来假设提前建设账户系统。

JSON 导入导出必须从第一版就定义：

- schemaVersion、导出时间、时区与日历标识。
- 稳定 UUID，导入幂等；同一文件重复导入不会重复生成数据。
- 导入前校验，未知版本拒绝并给出可操作提示。
- 冲突策略可解释，不以「最后写入」静默覆盖用户手动编辑过的日子。
- 导出内容与 CloudKit 内容遵循同一数据最小化边界。

### 隐私承诺

产品继续 local-first。**CloudKit 默认关闭**：不开启记录功能的用户，网络行为与今天完全一致，
引导页现有的隐私表述继续成立。只有在用户第一次进入记录 Tab 时，才明确询问是否开启同步。

开启后的准确表达是：

> 数据默认保存在你的设备上。开启 iCloud 同步后，记录会通过你的 iCloud 私有数据库在 Apple
> 设备间同步；我们不建立应用账户，也无法从开发者后台浏览你的私人记录。

上线前必须完成：

- 重新评估 App Store 隐私标签，而不是简单把「使用 CloudKit」等同于开发者收集数据。
- 逐条复核 19 个 locale 里的隐私文案。至少 `onboardingPrivacyBody`、`onboardingOfflineBody`、
  `onboardingPrivacyWorkBody` 与落地页的 `landingFeature3Body` 需要改写成「默认只在本机；
  开启同步后进入你自己的 iCloud」，不能继续笼统声称「不会发起网络请求」。
- 在应用内提供数据范围说明、同步状态、导出与删除入口。
- 删除行为明确区分「从此设备移除」和「从 iCloud 及所有设备删除」。
- 对 iCloud 未登录、离线、空间不足、账户切换和首次大批量下载提供可理解的状态。
- 审查 CloudKit schema，确认没有薪资、设备标识、定位或不必要的使用行为字段。
- 中国大陆 iCloud 的措辞停在「同步到你自己的 iCloud，我们没有服务器，也拿不到你的数据」。
  **不要**在任何语言里升级成「只有你和 Apple 能碰」（大陆由云上贵州运营，不准确）或
  「端到端加密」（私有库默认不是，除非用户开了高级数据保护）。这一句对 19 种语言都成立，
  不需要给简中开特例。

## P0A — 本地记录基础

P0A 的目标不是抢救「每天正在流失的真实工时」。真正会随时间产生、且无法事后自动重建的，
是少量应用观察；排班历史则可以通过职业阶段与排班版本稳定表达，用户编辑更是随时可补。

### 1. 三层优先级：一天到底怎么算出来的

任何一天的结论都由这条链决定，**顺序固定，且每一层都可以单独解释**：

~~~
当日覆盖 DayOverride        用户说了算，最高优先级；删除它就回落到下一层
      ↓ 没有覆盖时
日历例外 CalendarException  法定假日 / 周末补班，回答「这天算不算工作日」
      ↓ 没有例外时
排班快照 ScheduleSnapshot   当时生效的排班，连续时间轴的默认底图

应用观察 WorkObservation    不在这条链里。它只附着在结果上作为注解，永远不改变结论。
~~~

这条链是整份设计的骨架，UI 的「数据来源」说明就是它的直接投影：点开某一天，先告诉用户
这天走的是哪一层，再展示细节。

### 2. 职业阶段与排班快照

~~~swift
struct CareerPeriod {
    var id: UUID
    var startsOn: Date
    var endsBefore: Date?
    var label: String?
    var timeZoneIdentifier: String
    var calendarIdentifier: String
}

struct ScheduleSnapshot {
    var id: UUID
    var careerPeriodID: UUID
    var schemaVersion: Int
    var effectiveFrom: Date
    var configurationData: Data
    var fingerprint: String
}
~~~

约束：

- 职业阶段是长期时间轴的来源；一个职业阶段可以包含多次排班修订。
- 修改当前排班时，在所属职业阶段内新建快照并指定生效日期，不回写整个历史。
- 快照保存足以重放共享规则的版本化配置。fingerprint 只用于识别相同配置，不能代替配置本身。
- **快照不含薪资。** 它只保存班次形态，薪资继续由用户设置提供，也因此不进 CloudKit。
- 跨夜班次按班次开始日归档，不能用本地日期唯一约束拆成两天。
- 工作片段、午休、跨夜、计划结束和加班延长继续由共享 TypeScript 规则计算，再生成
  CountdownRules.js 供 iOS 使用。Swift 不实现第二套排班算法。
- 时区变化必须保留原阶段的语义，不能因为用户旅行就把历史班次整体平移。

**共享规则需要一个按区间批量展开的接口。** 年视图要展开 365 天 × N 年，人生视图要展开整段
职业生涯，逐日调用 JS 桥不可行。这个接口的形态与性能预算属于 P0A 的验收项，不能留到 P1
才发现。

### 3. 应用观察日志

~~~swift
enum WorkObservationKind: String {
    case timerSurfaceFirstSeen
    case countdownStarted
    case countdownStopped
    case overtimeDeclared
}

struct WorkObservation {
    var id: UUID
    var shiftAnchorDate: Date
    var occurredAt: Date
    var kind: WorkObservationKind
    var valueData: Data?
    var scheduleSnapshotID: UUID
    var schemaVersion: Int
}
~~~

观察日志遵守以下边界：

- 字段与 UI 不使用 actualStart、actualEnd 或「实际上班 / 下班」命名。
- 第一次进入计时页只表示「首次查看」；启动倒计时只表示「启动计时」。
- 计时到零只表示越过计划边界，不能自动生成离岗时间。
- 登记加班表示用户声明了计划延长，不等于已经完成该时长。
- 只记录以上四种事件，**不采集每次前后台切换和连续前台时长**。
- **完整保留每次主动计时**：一天可以有多条开始 / 停止，不折叠、不自动清理。体量极小
  （一年千余条），而「今天反复开关了三次」本身就是有意义的细节。
- **只用于解释单日**，不参与任何周 / 月 / 年 / 人生视图的聚合指标。
- 用户可以删除观察日志；删除不影响薪资、工时统计或任何结论。

### 4. 当日覆盖：确认与修改是同一件事

~~~swift
enum DayOverrideKind: String {
    case confirmedAsScheduled   // 我核对过，这天就是按排班走的
    case customSegments         // 这天其实是这样
    case notWorking             // 这天没上班（请假、调休、临时休息）
}

struct DayOverride {
    var id: UUID
    var shiftAnchorDate: Date
    var kind: DayOverrideKind
    var segmentsData: Data?      // kind == .customSegments 时为完整的当日工作片段
    var note: String?
    var editedAt: Date
    var scheduleSnapshotID: UUID // 编辑时生效的排班，用来解释「相对排班改了什么」
    var schemaVersion: Int
}
~~~

- **一天最多一条。** 「确认这天属实」只是覆盖值恰好等于排班的特例，不需要第二张表。
- **清空 = 删除这一条**，那天自然回落到日历例外或排班默认。不需要「已清空」这种状态位。
- `segmentsData` 存的是**完整的当日工作片段**，不是 start / end 两个点——它必须能表达午休
  切分、跨夜和加班延长，否则用户一改就丢结构。
- **过去、今天、未来都能覆盖。** 未来日期的覆盖就是「临时调班」：下周三 10 点上班、下周五
  请假，当天的倒计时、提醒与小组件都按覆盖走，用户不必为一天去改全局排班再改回来。
- 覆盖是用户的话，因此**没有「应用觉得你改错了」这种校验**；只做基本合法性检查（片段不
  交叉、结束晚于开始）。
- 覆盖影响工时统计与人生视图，**不影响收入**——见「收入口径」。

### 5. 日历例外：节假日与调休补班

~~~swift
enum CalendarEffect: String {
    case rest   // 这天不上班（法定假日）
    case work   // 这天要上班（周末补班）
}

enum CalendarExceptionOrigin: String {
    case user
    case bundled
}

struct CalendarException {
    var id: UUID
    var date: Date
    var effect: CalendarEffect
    var origin: CalendarExceptionOrigin
    var regionIdentifier: String?  // origin == .bundled 时标记数据来源地区
    var datasetVersion: String?    // 内置数据的版本，便于整批替换
    var label: String?
    var schemaVersion: Int
}
~~~

- **必须双向。** 中国的调休不只是「排除假日」，它还会把周末变成工作日。只做 `.rest` 的
  设计一开始就是错的。
- 首版只开放 `origin == .user` 的手动标记。`bundled` 相关字段现在就留好，将来接入内置
  节假日数据时不用改 schema，也不用现在就承担每年跟随公告更新数据的责任。
- 例外按**班次锚点日**匹配，与排班判定工作日的口径一致，跨夜班次不会因为跨过午夜而落到
  另一天的例外上。
- 与当日覆盖的分工：**例外回答「这天算不算工作日」，覆盖回答「这天具体怎么上的」**。
  法定假日和补班是外部日历，属于例外；请假是个人决定，属于覆盖。

### 7. 每日摘要是派生缓存，不是事实表

~~~swift
struct DailyWorkSummary {
    var id: UUID
    var shiftAnchorDate: Date
    var resolvedFrom: DayResolutionLayer  // .override / .calendarException / .schedule
    var scheduleSnapshotID: UUID
    var resolvedSegmentsData: Data
    var resolvedDurationMs: Int64
    var declaredOvertimeMs: Int64
    var isScheduledWorkday: Bool
    var observationCount: Int
    var firstObservationAt: Date?
}
~~~

- 摘要从排班快照、日历例外、当日覆盖与共享规则派生，可随时重建。
- 摘要只作为设备本地缓存，**不进入 CloudKit**；同步基础数据后由每台设备重新计算。
- `resolvedFrom` 直接对应三层优先级，UI 的来源说明读这一个字段即可。
- 不使用 date 唯一约束假设一天只有一次会话。
- 真实来源是职业阶段、排班快照、日历例外与用户覆盖；摘要只服务查询与图表性能。

### 8. 收入口径

这是最容易出现「看起来像 bug 其实是设计」的地方，所以口径写死在这里。

**记录页的收入 = 区间内已完成的排班工作日 × 日薪。** 不含今天，不含加班，不受当日覆盖
影响。日薪沿用共享规则现有定义（月薪 ÷ 月工作日 × 年终奖折算系数）。

由此产生三个必须在 UI 上讲清楚、而不是掩盖的结果：

1. **记录页和计时页的数字会不一样。** 计时页的 `periodSummary` 含今天按 `payRatio` 的折算，
   而 `payRatio` 不封顶、含加班。两者口径不同是有意的：一个是「此刻赚到多少」，一个是
   「已经完成的日子」。不要在同一屏并列这两个数。
2. **改薪资设置会改写历史收入数字。** 因为薪资不进排班快照（快照要同步，薪资不该同步），
   历史收入始终是「按当前薪资推算」。所以记录页的收入必须带这个限定词，沿用计时页已有的
   「按当前设置推算」语汇。
3. **标记为请假的那天，工时归零但收入照算。** 应用不知道这是带薪年假还是无薪事假，所以
   不猜。这条要写在覆盖编辑页的说明里，否则一定会被当成 bug 报上来。

登记加班继续按现状影响计时页的实时收入（`payRatio` 口径不变）——那是排班链路上用户的
主动设置，不是「观察改写了收入」。但它**不进记录页的历史收入**。

记录页的收入沿用现有的 `hideEarnings` 与生物识别门禁，不因为换了一个页面就绕过。

### 9. 文案口径

可以说：

- 「今天的排班从 09:00 开始」
- 「你在排班前 18 分钟首次查看了倒计时」
- 「根据你启动倒计时的时间，今天可能比排班早开始 18 分钟」
- 「今天登记了 1 小时加班」
- 「过去 30 天，排班约占清醒时间的 56%」
- 「你把这天改成了 10:00–19:00」

观察性总结可以用更自然的「可能提前开始」帮助用户回望，但**摘要句与来源详情必须同版上线**：
详情要显示它来自哪次主动计时，并明确不是考勤结论。首次查看只能写成「首次查看」，不能升级
成「开始工作」。

不能说：

- 「你今天 08:42 上班了」
- 「你迟到了 5 小时 30 分钟」
- 「你实际工作了 9 小时」
- 「你今天准时下班」——除非这天有用户覆盖，且 UI 同时标注为用户记录

### 10. 事件接入

| 事件 | 现有钩子 | 写入 | 明确不推断 |
| --- | --- | --- | --- |
| 当日首次进入计时页面 | `RootView` 的场景/路由入口 | timerSurfaceFirstSeen | 不是上班 |
| 用户主动开始倒计时 | `OffWorkStore.startCountdown` | countdownStarted | 不是工作开始 |
| 用户主动停止倒计时 | `OffWorkStore.stopCountdown` | countdownStopped | 不是离岗 |
| 用户登记加班 | `OffWorkStore.applyOvertime` | overtimeDeclared | 不是已完成加班 |
| 倒计时越过结束边界 | `TimerVisualPhase` 的 `.completed` | 更新派生状态 | 不生成实际下班 |
| 跨日结算 / App 重启恢复 | `reconcileCountdownSession` + `.NSCalendarDayChanged` | 幂等重连已有观察 | 不重复记一次开始 |

这些钩子今天都在 [OffWorkStore.swift](../src-mobile/ios/App/App/Native/Models/OffWorkStore.swift)
里，是唯一的写入点；接入时不需要新机制。

写入通过单一 RecordCoordinator 串行化，事件 UUID 和业务幂等键共同防止重启、重复点击、
CloudKit 回放造成重复记录。

### 11. 本地持久化边界

- 主 SwiftData store 放在应用私有容器，不放进 App Group。
- App Group 继续只承载无薪资的 WidgetSnapshot 投影；小组件不直接打开主数据库。
- 所有同步实体使用稳定 UUID，不依赖 CloudKit 不支持的唯一性约束。
- CloudKit 兼容模型中的关系需按可选关系设计，并由业务校验保证完整性。
- SwiftData schema 与 JSON schema 解耦，避免未来数据库迁移直接锁死 Android 导入。
- **P0A 建立的表**：CareerPeriod、ScheduleSnapshot、WorkObservation、DayOverride、
  CalendarException、LifeProfile、DailyWorkSummary（本地）。P2 的任务与专注表随 P2 建立——
  新增实体在 SwiftData / CloudKit 里是轻量迁移，改已有实体的字段才是贵的，所以字段现在
  想清楚（见 P2），表不必提前部署到生产 schema。
- P0A 即使不提供完整记录页，也至少需要数据说明、诊断导出和删除能力供测试。

## P0B — CloudKit 同步与数据控制

CloudKit 在本地模型和迁移测试稳定后接入，不能把同步调试与记录语义同时塞进第一笔改动。

验收矩阵：

| 场景 | 预期 |
| --- | --- |
| 从未开启同步 | 网络行为与今天一致，隐私文案原样成立 |
| 未登录 iCloud / iCloud Drive 关闭 | 本地照常工作，状态可解释 |
| 离线创建和编辑 | 联网后合并，不丢用户覆盖 |
| iCloud 空间不足 | 本地保留，提示不会冒充已同步 |
| 两台设备改同一天 | 冲突可检测、可解释、可恢复，用户覆盖优先于自动派生 |
| Apple Account 切换 | 不把前一账户的私有数据误传给新账户 |
| 首次安装下载大量历史 | UI 可用，有同步进度，不阻塞计时 |
| 删除记录 / 删除全部云数据 | 所有设备最终一致，用户收到明确结果 |
| 时区与夏令时变化 | 班次锚点和历史比例不漂移 |
| Production schema | 发布前部署并由真实容器验证 |
| JSON 往返 | 导出后清空再导入，语义与 UUID 保持一致 |

## P1 — 记录 Tab

### 入口与导航

记录是**第三个 Tab**：计时 / 记录 / 设置。人生视图是记录 Tab 内的一个级别，不单独占 Tab。
理由是发现率：付费墙在这个 Tab 后面，免费用户至少要看得见它的存在。

实现上要注意 `OffWorkStore` 现在把导航栈写死成二选一投影（`activePath` 在 timerPath 与
settingsPath 之间挑），横屏又是单一 NavigationStack 服务两个 Tab。加第三个 Tab 要先把这个
投影改成按 Tab 索引，而不是再加一个 if。

### 记录页的三层表达

记录页同时表现三层信息，但视觉权重不同：

1. **结论层**：这一天最终算成什么——来自覆盖、例外或排班，占主要视觉权重。
2. **来源层**：这个结论走的是哪一层，一句话说清，可点开。
3. **观察层**：首次查看、开始 / 停止计时等小标记，只在单日详情里出现。

### 周 / 月 / 年

- 周视图：结论片段作为主条；观察以点或细线附着，避免把「打开应用」画成工作柱。
- 月视图：热力图按当天结论时长着色；用户覆盖过的日子有明确但克制的标记。
- 年视图：展示工作占比与节奏密度。没有观察日志的日期仍有排班底图，不出现大面积假空白。
- 点击某日先解释来源，再显示细节：「按当时排班」「法定假日 / 补班」「你改过这天」。
- 每一天都可以就地编辑或清空，编辑入口不藏在二级菜单里——这是修正权在用户手里的具体形式。

### 核心指标

默认指标：

- 工作日数与工作总时长（按三层结论计算）。
- 工作占全部 24 小时的比例。
- 工作占预计清醒时间的比例。
- 登记的加班时长——始终保留「登记」限定词。
- 最长连续工作天数。
- 除去工作与睡眠后，预计属于自己的清醒时间。
- 已完成工作日的收入——带「按当前薪资推算」限定词。

**不做**「准时率」「迟到次数」「早退次数」，也不做任何基于观察的聚合指标。观察只解释单日。
如果以后要做准时率，前提是它完全建立在用户覆盖之上，并命名为「你记录的」。

### 人生视图

人生视图不是精确账本，也不是死亡倒计时。它把童年、学习、工作、睡眠、退休与真正属于自己的
时间放在同一个尺度上，让用户感受到：

> 工作很重要，但它不是人生的全部。看见它的边界，才更有机会保护边界之外的生活。

**最小输入**：出生日期或出生年份、开始工作的日期或年龄、预计退休年龄、平均睡眠时长、当前
职业阶段与排班。可选：用少量职业阶段描述过去明显不同的工作，不要求逐日补录。

**计算口径**：

- 右边界是**退休**，不假设寿命，不画「你还剩多少周」。
- 历史没有覆盖时，使用对应职业阶段的排班推算，并明确标注。
- 不要求用户准确重建上一份工作的每个班次；宏观一致比伪精确更重要。
- 周格使用连续日期 / 周索引计算，不把每年硬编码成 52 周。
- 工作时间始终基于共享规则展开的有效 segments，不是简单的开始到结束相减。
- 未来时间是情景推演，不是预言；退休年龄与睡眠时长均可调整。

**三种数据状态**：

| 状态 | 人生视图表达 |
| --- | --- |
| 排班推算（过去） | 稳定底色，标注「按当时排班估算」 |
| 排班推演（未来） | 纹理或透明度区别，标注「如果保持当前节奏」 |
| 用户覆盖 | 单独图例，可编辑、可撤销 |

**情绪与交互边界**：

- 默认展示比例与可获得的非工作时间，而不只展示「被工作拿走了多少」。
- 不发送任何人生尺度的推送，不做同龄人排名。
- 不用红色惩罚工作多的用户，也不把工作少包装成道德优越。
- 非工作时间不等于需要提高利用率的生产力空间。
- 支持隐藏具体年龄数字（`hidesExactAges`），只看年度与职业阶段比例。
- 文案承认照护、通勤、家务等同样会占据生活，但首版不擅自替用户分类。

## P2 — 任务与专注：服务当下，不扩张工作

表随 P2 建立，但字段现在定下来，以免届时回头拆记录层。

~~~swift
struct FocusTask {
    var id: UUID
    var createdAt: Date
    var plannedForDate: Date?     // 归属的班次锚点日；nil = 未排期
    var title: String
    var estimatedPomodoros: Int
    var completedAt: Date?
    var sortIndex: Int
    var schemaVersion: Int
}

enum FocusEndReason: String {
    case completed
    case stoppedByUser
    case stoppedAtBoundary   // 撞上午休 / 下班 / 加班结束
    case abandoned           // 重启后发现的孤儿会话
}

struct FocusSession {
    var id: UUID
    var taskID: UUID?
    var shiftAnchorDate: Date
    var startedAt: Date
    var plannedEndAt: Date       // 绝对截止时间；后台不执行代码
    var endedAt: Date?
    var endReason: FocusEndReason?
    var schemaVersion: Int
}
~~~

行为约束：

- 一个任务只有标题、预估几个番茄、是否完成。没有项目、标签、优先级或统计面板。
- 一个专注段不得静默跨过午休、微休息、排班结束或加班结束；到边界时温和收束或询问延续。
- 排不下的任务明确告诉用户「今天排不下了」，不做愧疚感设计；下班时未完成的静默顺延。
- 休息与边界计算继续来自共享 TypeScript 规则，不在 Swift 复制一套。
- 前台使用动画计时；进入后台后依赖 `plannedEndAt` 与系统通知 / Live Activity。不能把
  「后台运行」设计成持续执行 Swift 代码。
- 决定复用一条统一 Live Activity，还是工作倒计时与专注各一条；若并存，要定义系统排序所需
  的 relevance 和用户看到的主活动。
- 启动、更新、结束沿用同一串行化生命周期所有权，避免专注与工作倒计时互相撤掉。
- **专注分钟不汇总成工作时长，不进收入，不改变任何工作占比。**

## 关键验收场景

1. 排班 09:00 开始，08:42 只打开应用：当天仍显示 09:00 排班；只可说「提前 18 分钟首次查看」。
2. 08:42 主动启动倒计时：可以说「根据计时记录，今天可能提前开始 18 分钟」，但不记成事实。
3. 14:30 第一次打开应用：记录页不说迟到，也不把工作时长缩短到 14:30 以后。
4. 一周没打开应用：周、月、人生视图仍按有效排班连续展示；观察层为空但不是历史空洞。
5. 同一天多次开始 / 停止倒计时：全部保留且幂等，不累计成工时，不重复计算薪资。
6. 22:00–06:00 跨夜班次：归属于开始日，并使用共享规则展开的 segments。
7. 倒计时越过计划结束：不自动生成实际下班、准时或早退结论。
8. 登记一小时加班后关闭应用：只显示「登记了一小时加班」，不说已工作一小时。
9. 从下月开始更换排班：旧职业阶段不变，新快照只影响生效日之后。
10. 把某天改成 10:00–19:00：那天的工时与人生视图跟着变，收入不变，来源标为「你改过这天」。
11. 清空某天的覆盖：立刻回落到日历例外或排班默认，不留「已清空」痕迹。
12. 把下周五标为请假：当天倒计时与提醒都不响，工时为零，收入照算，说明文案解释了为什么。
13. 把某个周六标为补班：那天变成工作日，参与统计与倒计时，与法定假日方向相反。
14. 涨薪后回看去年：收入数字变了，但页面明确写着「按当前薪资推算」。
15. 未登录 iCloud、离线、额度已满或切换账户：本地数据不丢、不被错误账户接管，状态可解释。
16. 订阅到期：记录、人生视图、专注不可见，但查看导出与删除自己数据的入口仍在，倒计时照常用。

## 一句话原则

**看见工作如何占据时间，但不让工具越权定义用户的人生——需要改的时候，改的人是用户。**
