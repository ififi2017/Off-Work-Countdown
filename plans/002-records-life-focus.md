# 002 — 从「倒计时」到「记录」：工作占比、人生视图与专注

- **Status**: DRAFT
- **Reviewed against**: a7a4e1a
- **Severity**: HIGH
- **Category**: Product values / Architecture / Persistence / Privacy / New surfaces
- **Estimated scope**: 五个可独立验收的交付阶段；不再用文件数量估算复杂度

## 出发点：这个 App 现在没有记忆，但「推算」不是缺陷

当前应用保存排班、薪资与偏好，却没有跨日的历史记录：

- 「本周工作天数 / 小时」来自当前排班规则的推算，不是考勤。
- 应用没有保存用户何时第一次打开计时页、何时开始或停止一次倒计时。
- 用户几天不打开应用，就不会留下任何使用事件。

这不意味着我们应该把应用打开时间补成「真实上下班时间」。

有人会提前到公司后打开应用等待计时，有人下午无聊才来看一眼，也有人几天都不会打开。
应用处于前台，只能证明用户看过这个工具，不能证明他正在工作；倒计时结束，也不能证明
用户已经离开公司。早来和晚走更不必然改变工资。

因此，**用户主动设置的排班与职业阶段，才是工作如何占据生活的稳定底图**。应用事件可以
作为补充观察，帮助用户回望「今天比排班早多久打开」「登记了多少加班」，但不能冒充考勤、
薪资依据或关于实际工时的铁证。

## 我们为什么要做「记录」

倒计时回答的是今天：「还要多久下班？」

记录与人生视图回答的是更长的问题：

- 工作在一天、一个月、一年里占去了多少时间？
- 除去工作和睡眠，真正属于自己的清醒时间还有多少？
- 如果按现在的节奏走到退休，一生会有多少时间交给工作？
- 工作之外，还有哪些时间值得被看见、被保护、被认真安排？

它的价值不在于复刻一份精确考勤表，而在于把抽象的年月变成可感知、可触摸的比例。我们希望
用户看清工作在生命里的位置，从而更有意识地维护 work-life balance，而不是被一套并不可靠的
「实际工时」数字审判。

### 产品价值观

1. **排班是底图，不是次等数据。** 对多数固定工作的用户，约定好的班次比应用在线时间更能
   表达工作长期占据了多少生活。
2. **观察是线索，不是事实。** 打开应用、启动计时、登记加班等事件可以丰富回顾，但必须以
   「观察到」「登记了」来表达。
3. **允许近似，但必须诚实。** 人生尺度本来就是推演。我们可以使用默认寿命、退休年龄和历史
   排班，但要把假设说清楚，并允许用户修改。
4. **解释权属于用户。** 只有用户明确确认的数据，才可以进入「用户确认」层；应用不能替用户
   判断他是否迟到、早退或真的加班。
5. **时间属于用户，不属于生产力评分。** 非工作时间不是等待被填满的空白，不提供道德化提醒、
   同龄人排名或用红色制造焦虑。
6. **记录不自动改写收入。** 早到、晚走、打开应用和倒计时会话均不改变薪资计算；薪资继续遵守
   用户设置与共享业务规则。

### 明确不做什么

- 不做考勤、雇员监控或定位追踪。
- 不把前台停留、倒计时会话或通知交互累计成「真实工时」。
- 不把记录包装成工资结算、劳动争议或绩效评估的证据。
- 不要求用户重建每一份工作的逐日历史，才允许查看人生视图。
- 不因为某天没有打开应用，就在时间轴上制造「未知的一天」或历史空洞。
- 不用精确到分钟的幻觉掩盖数据本身只是排班推算。

## 已定方向

| 议题 | 决定 |
| --- | --- |
| 核心口径 | **职业阶段 / 排班为主，应用观察为辅，用户确认独立存在** |
| 数据表达 | 计划、观察、确认三层并存；禁止用一枚 source 覆盖整天 |
| 无使用事件的日期 | 仍按当时有效的排班展示，不留空、不虚构实际记录 |
| 跨平台 | iOS 优先；Android 以版本化 JSON 导入导出衔接；Web 后定 |
| 同步 | 本地永远可用；Apple 平台可通过 CloudKit 私有库同步 |
| 订阅 | 先建立可验证的权益层；记录的留存、导出和删除不因订阅到期失效 |
| 专注 | 轻量、尊重班次边界；不把专注分钟伪装成工作时长 |

## 数据与平台边界

### CloudKit 与 Android

CloudKit private database 适合 Apple 设备之间的私有同步，但不是 Android 的同步后端，也不应被
描述成跨平台云账户。首版边界是：

- iPhone / iPad / Mac：同一 Apple Account 下可同步。
- 没有登录 iCloud、iCloud Drive 关闭、离线或额度不足：本地记录仍可创建、查看和修改。
- Android：首发不承诺 CloudKit 同步，版本化 JSON 是一等迁移通道。
- Web：只有在隐私、付费和使用场景明确后再决定，不为未来假设提前建设账户系统。

JSON 导入导出必须从第一版就定义：

- schemaVersion、导出时间、时区与日历标识。
- 稳定 UUID，导入幂等；同一文件重复导入不会重复生成数据。
- 导入前校验，未知版本拒绝并给出可操作提示。
- 冲突策略可解释，不以「最后写入」静默覆盖用户确认的数据。
- 导出内容与 CloudKit 内容遵循同一数据最小化边界。

### 隐私承诺

产品继续 local-first，但启用 CloudKit 后，文案不能再笼统声称所有数据「只保存在本机」。
准确表达应是：

> 数据默认保存在你的设备上。开启 iCloud 同步后，记录会通过你的 iCloud 私有数据库在 Apple
> 设备间同步；我们不建立应用账户，也无法从开发者后台浏览你的私人记录。

上线前必须完成：

- 重新评估 App Store 隐私标签，而不是简单把「使用 CloudKit」等同于开发者收集数据。
- 在应用内提供数据范围说明、同步状态、导出与删除入口。
- 删除行为明确区分「从此设备移除」和「从 iCloud 及所有设备删除」。
- 对 iCloud 未登录、离线、空间不足、账户切换和首次大批量下载提供可理解的状态。
- 审查 CloudKit schema，确认没有薪资、设备标识、定位或不必要的使用行为字段。
- 中国大陆 iCloud 的基础设施说明只使用 Apple 已公开且能够长期维护的中性措辞。

## P0A — 本地记录基础

P0A 的目标不是抢救「每天正在流失的真实工时」。真正会随时间产生、且无法事后自动重建的，
是少量应用观察；排班历史则可以通过职业阶段与排班版本稳定表达。

### 1. 职业阶段与排班快照

~~~swift
struct CareerPeriod {
    var id: UUID
    var startsOn: Date
    var endsBefore: Date?
    var label: String?
    var timeZoneIdentifier: String
    var calendarIdentifier: String
}

struct ScheduleSnapshot {
    var id: UUID
    var careerPeriodID: UUID
    var schemaVersion: Int
    var effectiveFrom: Date
    var configurationData: Data
    var fingerprint: String
}
~~~

约束：

- 职业阶段是长期时间轴的来源；一个职业阶段可以包含多次排班修订。
- 修改当前排班时，在所属职业阶段内新建快照并指定生效日期，不回写整个历史。
- 快照保存足以重放共享规则的版本化配置。fingerprint 只用于识别相同配置，不能代替配置本身。
- 跨夜班次按班次开始日归档，不能用本地日期唯一约束拆成两天。
- 工作片段、午休、跨夜、计划结束和加班延长继续由共享 TypeScript 规则计算，再生成
  CountdownRules.js 供 iOS 使用。Swift 不实现第二套排班算法。
- 时区变化必须保留原阶段的语义，不能因为用户旅行就把历史班次整体平移。

### 2. 应用观察日志

~~~swift
enum WorkObservationKind: String {
    case timerSurfaceFirstSeen
    case countdownStarted
    case countdownStopped
    case overtimeDeclared
}

struct WorkObservation {
    var id: UUID
    var shiftAnchorDate: Date
    var occurredAt: Date
    var kind: WorkObservationKind
    var valueData: Data?
    var scheduleSnapshotID: UUID
    var schemaVersion: Int
}

enum UserConfirmationKind: String {
    case startedWork
    case endedWork
    case completedOvertime
}

struct UserConfirmation {
    var id: UUID
    var shiftAnchorDate: Date
    var occurredAt: Date
    var kind: UserConfirmationKind
    var confirmedValue: Date?
    var scheduleSnapshotID: UUID
}
~~~

观察日志遵守以下边界：

- 字段与 UI 不使用 actualStart、actualEnd 或「实际上班 / 下班」命名。
- 第一次进入计时页只表示「首次查看」；启动倒计时只表示「启动计时」。
- 计时到零只表示越过计划边界，不能自动生成离岗时间。
- 登记加班表示用户声明了计划延长，不等于已经完成该时长。
- 只记录形成产品价值所需的最小事件，不采集每次前后台切换和连续前台时长。
- 用户可以删除观察日志；观察日志不单独改变薪资或考勤结论。
- 用户确认是独立实体，不混入观察类型；只有明确、可撤销的用户动作才能产生，并记录确认口径。

### 3. 每日摘要是派生缓存，不是事实表

~~~swift
struct DailyWorkSummary {
    var id: UUID
    var shiftAnchorDate: Date
    var scheduleSnapshotID: UUID
    var scheduledSegmentsData: Data
    var scheduledDurationMs: Int64
    var declaredOvertimeMs: Int64
    var firstSeenAt: Date?
    var lastSeenAt: Date?
    var confirmedStartedAt: Date?
    var confirmedEndedAt: Date?
}
~~~

- 摘要从排班快照、共享规则和观察日志派生，可随时重建。
- 摘要只作为设备本地缓存，不进入 CloudKit；同步基础数据后由每台设备重新计算。
- 不使用 date 唯一约束假设一天只有一次会话。
- 计划、观察、确认可以同时存在，不能用 projected / session / manual 三选一。
- 真实来源是职业阶段、排班快照和观察事件；摘要只服务查询与图表性能。

### 4. 文案口径

可以说：

- 「今天的排班从 09:00 开始」
- 「你在排班前 18 分钟首次查看了倒计时」
- 「根据你启动倒计时的时间，今天可能比排班早开始 18 分钟」
- 「今天登记了 1 小时加班」
- 「过去 30 天，排班约占清醒时间的 56%」

观察性总结可以用更自然的「可能提前开始」帮助用户回望，但详情必须显示它来自哪次主动计时，
并明确不是考勤结论。首次查看只能写成「首次查看」，不能升级成「开始工作」。

不能说：

- 「你今天 08:42 上班了」
- 「你迟到了 5 小时 30 分钟」
- 「你实际工作了 9 小时」
- 「你今天准时下班」——除非用户明确确认，且 UI 同时标注为用户记录

### 5. 事件接入

| 事件 | 写入 | 明确不推断 |
| --- | --- | --- |
| 当日首次进入计时页面 | timerSurfaceFirstSeen | 不是上班 |
| 用户主动开始倒计时 | countdownStarted | 不是工作开始 |
| 用户主动停止倒计时 | countdownStopped | 不是离岗 |
| 用户登记加班 | overtimeDeclared | 不是已完成加班 |
| 倒计时越过结束边界 | 更新派生状态 | 不生成实际下班 |
| App 重启后恢复会话 | 幂等重连已有观察 | 不重复记一次开始 |

写入通过单一 RecordCoordinator 串行化，事件 UUID 和业务幂等键共同防止重启、重复点击、
CloudKit 回放造成重复记录。

### 6. 本地持久化边界

- 主 SwiftData store 放在应用私有容器，不放进 App Group。
- App Group 继续只承载无薪资的 WidgetSnapshot 投影；小组件不直接打开主数据库。
- 所有同步实体使用稳定 UUID，不依赖 CloudKit 不支持的唯一性约束。
- CloudKit 兼容模型中的关系需按可选关系设计，并由业务校验保证完整性。
- SwiftData schema 与 JSON schema 解耦，避免未来数据库迁移直接锁死 Android 导入。
- P0A 即使不提供完整记录页，也至少需要数据说明、诊断导出和删除能力供测试。

## P0B — CloudKit 同步与数据控制

CloudKit 在本地模型和迁移测试稳定后接入，不能把同步调试与记录语义同时塞进第一笔改动。

验收矩阵：

| 场景 | 预期 |
| --- | --- |
| 未登录 iCloud / iCloud Drive 关闭 | 本地照常工作，状态可解释 |
| 离线创建和编辑 | 联网后合并，不丢用户确认 |
| iCloud 空间不足 | 本地保留，提示不会冒充已同步 |
| 两台设备改同一职业阶段 | 冲突可检测、可解释、可恢复 |
| Apple Account 切换 | 不把前一账户的私有数据误传给新账户 |
| 首次安装下载大量历史 | UI 可用，有同步进度，不阻塞计时 |
| 删除记录 / 删除全部云数据 | 所有设备最终一致，用户收到明确结果 |
| 时区与夏令时变化 | 班次锚点和历史比例不漂移 |
| Production schema | 发布前部署并由真实容器验证 |
| JSON 往返 | 导出后清空再导入，语义与 UUID 保持一致 |

## P0C — StoreKit 权益基础

权益系统与记录数据分开建设。记录的创建、查看、导出和删除不能因为订阅到期而被锁住；未来
收费应针对增值分析、外观或自动化能力，而不是劫持用户自己的数据。

### 1. 可验证的权益来源

- 使用经过验证的 AppTransaction 和当前 entitlements。
- 持久化 originalPlatform，因为 iOS 与 macOS 的 originalAppVersion 口径不同。
- iOS 的历史买断判断按原始 **build number**，macOS 按原始
  **marketing version**；分别定义不可变 cutoff。
- Sandbox 的原始版本值不能用于验证历史用户迁移，必须用 StoreKit Testing 和真实 TestFlight
  场景覆盖。
- 不用「第一次看到这个值时就缓存」掩盖未验证或瞬时失败。

### 2. 先决定老用户获得什么

在写 cutoff 前，必须形成一张明确的权益矩阵：

| 用户 | 已有功能 | 未来记录基础 | 增值分析 / 专注 |
| --- | --- | --- | --- |
| cutoff 前买断用户 | 永久保留 | 是否永久获得，需决定 | 是否包含，需决定 |
| cutoff 后下载用户 | 免费范围 | 数据权利不受限 | 可订阅 |
| 当前订阅用户 | 按产品定义 | 数据权利不受限 | 已解锁 |
| 订阅到期用户 | 回到免费范围 | 数据仍可查看、导出、删除 | 停止增值能力 |

P0C 可以只交付内部权益基础和测试入口。真正开启订阅时，必须另行提供完整付费页：本地化价格、
周期、试用后价格、恢复购买、服务条款、隐私政策和清晰的自动续费说明，不能「零 UI 发版」。

## P1A — 记录视图：计划是主体，观察提供纹理

记录页同时表现三层信息，但视觉权重不同：

1. **计划层**：当时生效的排班，是连续时间轴的主体。
2. **观察层**：首次查看、开始 / 停止计时、登记加班等小标记。
3. **确认层**：用户主动确认的信息，以明确标签区别于推算。

### 周 / 月 / 年

- 周视图：排班片段作为主条；观察以点或细线附着，避免把「打开应用」画成工作柱。
- 月视图：热力图按计划工作时长着色；登记加班使用次级标记，不直接并入「实际时长」。
- 年视图：展示工作占比与节奏密度。没有观察日志的日期仍有排班底图，不出现大面积假空白。
- 点击某日先解释数据来源，再显示细节：「排班推算」「应用观察」「你确认的记录」。

### 核心指标

默认指标：

- 排班工作日与排班总时长。
- 工作占全部 24 小时的比例。
- 工作占预计清醒时间的比例。
- 登记的加班时长——始终保留「登记」限定词。
- 最长连续排班天数。
- 除去排班与睡眠后，预计属于自己的清醒时间。

观察指标：

- 有观察日志的样本天数。
- 首次查看倒计时相对排班开始的时间差。
- 主动启动倒计时早于排班的天数与平均提前量，标注「根据计时记录推测」。
- 计划结束后仍查看过应用的天数。
- 用户主动确认的记录数量。

默认不提供「准时率」「迟到次数」「早退次数」。如果以后增加，前提是存在低负担、明确且可撤销
的确认机制，并把指标命名为「你确认的记录」，不能从 App 行为自动推断。

薪资仍由共享规则按排班、有效片段和用户明确设置计算。观察日志不会改变历史收入；若未来允许
用户按日修正薪资，必须是单独、明确的财务编辑动作。

## P1B — 人生视图：看见工作，但不让工作定义人生

人生视图不是精确账本，也不是死亡倒计时。它想做的是把童年、学习、工作、睡眠、退休与真正
属于自己的时间放在同一个尺度上，让用户感受到：

> 工作很重要，但它不是人生的全部。看见它的边界，才更有机会保护边界之外的生活。

### 最小输入

- 出生日期或出生年份。
- 开始工作的日期或年龄。
- 预计退休年龄。
- 平均睡眠时长。
- 当前职业阶段与排班。
- 可选：用少量职业阶段描述过去明显不同的工作，不要求逐日补录。

### 计算口径

- 历史没有观察日志时，使用对应职业阶段的排班推算，并明确标注。
- 不要求用户准确重建上一份工作的每个班次；宏观一致比伪精确更重要。
- 周格使用连续日期 / 周索引计算，不把每年硬编码成 52 周。
- 工作时间始终基于共享规则展开的有效 segments，不是简单的开始到结束相减。
- 未来时间是情景推演，不是预言；退休年龄、寿命假设和睡眠时长均可调整。

### 四种数据状态

| 状态 | 人生视图表达 |
| --- | --- |
| 排班推算（过去） | 稳定底色，标注「按当时排班估算」 |
| 排班推演（未来） | 纹理或透明度区别，标注「如果保持当前节奏」 |
| 应用观察 | 只增加局部纹理，不改变整块时间的事实等级 |
| 用户确认 | 单独图例，可编辑、可撤销 |

### 情绪与交互边界

- 默认展示比例与可获得的非工作时间，而不只展示「被工作拿走了多少」。
- 不发送「人生只剩多少周」式推送，不做同龄人排名。
- 不用红色惩罚工作多的用户，也不把工作少包装成道德优越。
- 非工作时间不等于需要提高利用率的生产力空间。
- 支持隐藏具体年龄 / 寿命数字，只看年度和职业阶段比例。
- 文案承认照护、通勤、家务等同样会占据生活，但首版不擅自替用户分类。

## P2 — 任务与专注：服务当下，不扩张工作

专注能力保持轻量，并服从已经建立的时间边界：

- 快速记录当天最重要的一件事，可选普通计时或番茄节奏。
- 一个专注段不得静默跨过午休、微休息、排班结束或加班结束；到边界时温和收束或询问延续。
- 休息与边界计算继续来自共享 TypeScript 规则，不在 Swift 复制一套。
- 前台使用动画计时；进入后台后保存绝对截止时间，由系统通知和 Live Activity 展示。不能把
  「后台运行」设计成持续执行 Swift 代码。
- 决定复用一条统一 Live Activity，还是工作倒计时与专注各一条；若并存，要定义系统排序所需
  的 relevance 和用户看到的主活动。
- 启动、更新、结束沿用同一串行化生命周期所有权，避免专注与工作倒计时互相撤掉。
- 专注分钟不汇总成实际工作时长，也不自动拉长职业阶段中的工作占比。

## 交付顺序

### P0A — 本地语义与持久化

- 定稿职业阶段、排班快照、观察日志与派生摘要。
- 接入最小事件，完成跨夜、时区、重复启动和迁移测试。
- 保持主库私有，小组件只接收无薪资投影。

这一阶段先做，是因为观察事件会随时间积累；不是因为它们等于不可追回的真实考勤。

### P0B — CloudKit 与数据控制

- 同步、冲突、账户状态、Production schema。
- JSON 导入导出、查看和删除。
- 更新隐私文案与隐私标签评估。

### P0C — StoreKit 权益基础

- 定稿老用户权益矩阵。
- 验证平台差异、cutoff 和订阅状态。
- 付费开关与付费页作为独立上线决定。

P0B 与 P0C 不阻塞彼此，也不应和 P0A 混成一笔无法诊断的基础设施改动。

### P1 — 记录与人生视图

- 先交付周 / 月 / 年记录，再交付人生视图。
- 即使用户几天、几个月没有打开应用，排班底图仍连续存在。
- 所有比例都有来源说明，观察与确认不会伪装成事实。
- 所有用户可见文案纳入 19 个 UI locale；人生视图的长说明按内容页语言边界处理。

### P2 — 任务与专注

- 在记录语义和 Live Activity 所有权稳定后进入。
- 单独验收后台截止时间、班次边界、通知和多活动排序。

## 关键验收场景

1. 用户排班 09:00 开始，08:42 只打开应用：当天仍显示 09:00 排班；只可说「提前 18 分钟首次查看」。
2. 用户 08:42 主动启动倒计时：可以说「根据计时记录，今天可能提前开始 18 分钟」，但不能记成考勤事实。
3. 用户 14:30 第一次打开应用：记录页不说迟到，也不把工作时长缩短到 14:30 以后。
4. 用户一周没打开应用：周、月、人生视图仍按有效排班连续展示；观察层为空但不是历史空洞。
5. 用户同一天多次开始 / 停止倒计时：保留幂等事件，不累计成实际工时，不重复计算薪资。
6. 22:00–06:00 跨夜班次：归属于开始日，并使用共享规则展开的 segments。
7. 倒计时越过计划结束：不自动生成实际下班、准时或早退结论。
8. 用户登记一小时加班后关闭应用：只显示「登记了一小时加班」，不说已工作一小时。
9. 用户从下月开始更换排班：旧职业阶段不变，新快照只影响生效日之后。
10. 未登录 iCloud、离线、额度已满或切换账户：本地数据不丢、不被错误账户接管，状态可解释。
11. 订阅到期：历史仍可查看、导出和删除；只有明确的增值能力停止。

## 一句话原则

**看见工作如何占据时间，但不让工具越权定义用户的人生。**
