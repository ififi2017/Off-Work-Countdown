# 002 — 从「倒计时」到「记录」：工时留存、人生视图与专注

- **Status**: DRAFT
- **Commit**: feac4e9
- **Severity**: HIGH
- **Category**: Architecture / Persistence / Privacy / New surfaces
- **Estimated scope**: P0 约 8–12 个新文件 + 隐私文案、隐私标签与订阅配置；P1 / P2 各自独立发布

## 出发点：这个 App 现在没有记忆

代码现状（`feac4e9`）：

- **零历史持久化**。没有 SwiftData / CoreData / SQLite / 文件存储，全部状态是
  `OffWorkStore` 里 UserDefaults 支撑的标量。
- 计时页那个「本周 1.0 天 · 12.9 小时」是 `periodSummary` **按当前排班推算**出来的，
  UI 段标题字面就写着「按当前设置推算」。它不是记录。
- **会话开始时刻没有被存下来**。`recordActiveCountdownBoundary` 只写
  `activeCountdownEndAtMs`，`startCountdown` 不记录"几点点的开始"。

所以「记录」不是把已有数据露出来，而是**第一次引入持久化**。这是整份规划的支点，
也决定了下面 P0 的紧迫性。

## 已定的方向

| 决策 | 选择 |
| --- | --- |
| 数据边界 | **iCloud 私有库同步（CloudKit private database）** |
| 工时口径 | **排班推算为底，倒计时会话覆盖** |
| 平台范围 | iOS 优先；**Android 是可能的后续**；Web 视付费/使用情况再定 |
| 番茄钟形态 | **需要后台运行**，复用现有 Live Activity + 通知基础设施 |
| 历史回填 | **让用户选**，且要覆盖整个职业生涯——见下方「职业履历」 |
| 付费边界 | 不影响本规划。未来从买断改为「7/30 天试用 + 月/年/终身订阅」，付费墙加在 UI 层 |
| 上线节奏 | **地基（实记 + CloudKit + StoreKit）最先，再记录/人生视图，番茄钟最后** |

## 必须先解决的冲突：CloudKit 与 Android

**CloudKit 私有库是 Apple 独占的。** Android 端读不到，也没有官方客户端。
「用 CloudKit 同步」和「未来可能做 Android」这两条无法同时成立于同一套同步机制。

三条路：

1. **Apple 生态用 CloudKit，Android 本地存储，两边靠导出文件互通**（推荐）
   Apple 平台（iPhone / iPad / Mac）体验最好，Android 首发时不承诺同步。
   代价是跨生态换机要手动导一次。
2. **换跨平台后端**（自建或第三方）
   两端都能同步，但要运维、要账号体系，而且比 CloudKit **更**违背现有隐私定位。
3. **完全不做同步，只做导出/导入**
   最保守，但你已经否掉了。

**已定：采纳路线 1。** Android 目前是「可能」而非「早晚」，所以 P0 直接用
SwiftData + CloudKit 镜像，不为一个尚未立项的平台预付架构成本。

但**「导出/导入 JSON」要当成一等公民而不是补丁**——它同时是 Android 的迁移
通道、用户的备份出口、以及 CloudKit 出问题时的逃生舱。只有 Android 真正立项时
才重新评估路线 2。

## 隐私承诺必须改写，这是 CloudKit 的硬成本

现在引导页和落地页上这些话，开了 CloudKit 之后**就不再成立**：

| Key | 现在的话 | 问题 |
| --- | --- | --- |
| `onboardingPrivacyBody` | 「本 App 不会发起网络请求，也不会上传你的上班数据与薪资数据」 | 直接变成假话 |
| `onboardingOfflineBody` | 「不用账号，不用注册，也不依赖网络」 | CloudKit 需要 Apple ID |
| `onboardingPrivacyWorkBody` | 「上班时间和排班只保存在这台设备上」 | 不再只在这台 |
| `landingFeature3Body` | Web 落地页同类表述 | 同上 |

新的说法应该诚实且仍然有力，方向是：**数据同步到你自己的 iCloud，我们看不到，
也没有服务器**。这是事实，而且比原来的说法更经得起推敲。

**同时要改 App Store Connect 的 App 隐私标签**——一旦数据离开设备进入 iCloud，
「数据收集」的申报口径就变了。这一步不能漏，而且必须和启用 CloudKit **同版发布**。

### 中国大陆的 iCloud 是另一家公司运营的

这一条不影响技术方案，但影响文案能说到多满。大陆 Apple ID 的 iCloud 数据由
**云上贵州（GCBD）**运营并存储在境内，Apple 自己的隐私说明也是这么写的。所以
「同步到你自己的 iCloud，我们看不到」在大陆依然成立——**我们**确实看不到，没有
服务器这一点也没变——但「只有你和 Apple」这种更强的说法在简中文案里不准确。

结论：文案统一停在「同步到你自己的 iCloud 账号，我们没有服务器，也拿不到你的
数据」，不要在任何语言里升级成「只有 Apple 能碰」或「端到端加密」。前者在大陆
不准确，后者对 CloudKit 私有库本来就不准确（私有库默认不是端到端加密，除非用户
开了「高级数据保护」）。这样一句话对 19 种语言都成立，不需要给简中开特例。

## P0 — 现在就该打的地基（在任何「记录」界面之前）

> 唯一一件**拖一天就永久损失一天**的事。从排班能推算出过去哪天该上班，
> 但推算不出那天几点真正开始、几点真正结束、加了多久班。
> 3.1.7 如果不记，所有用户的真实历史就从「记录」发版那天才开始。

### P0.1 补上缺失的会话开始时刻

`startCountdown` 现在只记结束边界。加一个持久化的 `activeSessionStartedAtMs`。
一行字段，但没有它，「实际几点上的班」这个维度永远是空的。

### P0.2 定下 `ShiftRecord` 结构

一天一条，带版本号，字段建议：

```
schemaVersion
date                 本地日历日，主键
source               .projected | .session | .manual   ← 见下方说明
plannedStartAtMs     当天排班算出的计划上下班
plannedEndAtMs
actualStartAtMs?     倒计时会话真正开始的时刻
actualEndAtMs?       会话结束 / 越过下班线的时刻
overtimeEndAtMs?
breaks: [(start, end)]
scheduleFingerprint  写入当时的排班设置指纹        ← 见下方说明
```

**关于 `source`**：你选的是「推算为底、会话覆盖」，UI 上默认合并展示即可。
但**这个字段一定要存**——它几乎零成本，却让「这条是真的还是算的」永远可追溯。
没有它，将来想区分就得重新采集，那是不可逆的损失。我在提问时说过「今年已工作
2184 小时」混了虚构数据的顾虑，存这个字段是在你的选择之内把顾虑成本降到最低，
不改变你要的默认呈现。

**关于 `scheduleFingerprint`**：这条很容易被忽略，但会变成难查的 bug。
推算记录如果是**每次查询时现算**，那么用户改一次上下班时间，
"去年我工作了 2000 小时"就会**追溯性地变成另一个数字**。
所以推算记录必须**物化**——写入时算一次、存下来、之后不再重算，
并把当时的排班指纹一起存，用于解释和排错。

### P0.3 存储与同步选型

- **SwiftData 模型 + CloudKit 镜像**（`ModelConfiguration(cloudKitDatabase:)`），
  容器放 App Group，让小组件和未来的扩展也能读。
- **导出/导入 JSON schema 与 SwiftData 模型解耦**，单独定义、单独测试。
  这是 Android 与备份的契约，不能让它长成 SwiftData 的形状。
- SwiftData 模型本身不可移植到 Android，这是接受的代价；可移植性由 JSON 契约承担。

### P0.4 职业履历：回填不是「补今年」，是补一整段职业生涯

你选「让用户选」，理由是人生视图要算整个职业生涯，否则前十几年全是空白。
这个理由把回填的形态整个改掉了——**不能用今天的排班去推算十年前**。
十年里换过公司、改过作息，用当前设置铺满过去，得到的是一段看起来精确、
实际虚假的历史。

正确的形态是让用户声明**职业履历**：若干段时期，每段有起止和当时的作息。

```
CareerPeriod
  startDate / endDate?        endDate 为空表示至今
  label?                      「A 公司」，纯给用户自己看
  workdays / scheduleMode     那段时期的排班
  startMinutes / endMinutes
  lunch...
```

每段独立投影成 `.projected` 记录，物化写入，各自带自己的 `scheduleFingerprint`。
用户只填一段也完全可用——那就是最简单的情况。

**门槛要低**：首次进入记录页时，默认只从启用当天开始；想要完整人生视图的用户
再去补履历，并且界面上要说清楚那部分是推算。**不要**在引导页就问，
那会把一个轻量的倒计时 App 变成入职登记表。

**对指标的影响必须隔离**：「准点下班率」这类依赖实际下班时刻的指标，
**只能在 `.session` 记录上计算**，绝不能把 `.projected` 算进去——推算记录里
根本没有"实际几点走的"。人生视图用总量，那里 `.projected` 是合理的；
记录页的行为指标用实测，两者分开。这也是 `source` 字段必须存的第二个理由。

### P0.5 写入时机

已有的钩子基本够用，不需要新机制：

| 时机 | 现有钩子 |
| --- | --- |
| 开始倒计时 | `startCountdown` |
| 追加加班 | `applyOvertime` |
| 结束/停止 | `stopCountdown` |
| 跨过下班线 | 现有 `TimerVisualPhase` 已能判定 `.completed` |
| 跨日结算 | `reconcileCountdownSession()` + `.NSCalendarDayChanged` |

### P0.6 保留「推算 / 实测」的措辞区分

计时页那个「按当前设置推算」的段标题已经是对的，**不要在引入记录后把它改掉**。
它现在就在正确地标注投影，未来记录页也应沿用同一套语汇。

### P0.7 StoreKit：从买断改为试用 + 订阅

商业模式的切换属于地基，理由和记录一样——**它决定了后面每个功能能不能被卖**，
而且越晚切换，需要照顾的历史用户越多。

**最高风险项：已买断用户绝不能被挡在付费墙外。**

App 现在是 App Store / Mac App Store 上的买断制。切成订阅后，那些已经付过钱的
用户必须永久保留他们买到的东西。标准做法是读 `AppTransaction.shared` 的
`originalAppVersion`：**首次购买版本早于切换版本的用户，永久解锁**。

这件事有两个特点决定了它必须先做、且必须做对：

- **不可事后补救**。上线后才发现老用户被挡，他们已经在 App Store 打完一星了。
- **不依赖发布时机**。`originalAppVersion` 记录的是用户首次购买时的版本，
  不管我们哪一版切换，判定逻辑都成立。所以它可以、也应该提前落地并测试。

其余要点：

- **StoreKit 2**（`Transaction.currentEntitlements` / `AppTransaction`），
  部署目标 iOS 26 不需要考虑旧 API。
- **Universal Purchase**：App 同时在 iOS 和 Mac App Store 上架，
  `check:ios` 里也断言了这一点，订阅组要按共享方式配置。
- **试用期**（7/30 天）是 App Store Connect 里订阅组的 introductory offer，
  不是代码里的逻辑，但需要用 StoreKit Configuration 文件在本地测通。
- **订阅失效不能停止记录。** 这条是硬约束：用户订阅过期后，
  App 仍要继续写 `ShiftRecord`，只是不给看记录页。否则等他重新订阅，
  历史上会留下一个再也补不回来的洞——而这正是整份规划要避免的东西。
  付费墙只加在 UI 层，永远不加在写入层。

**P0 交付即可发版，不需要任何新界面。** 数据先攒着。

## P1 — 「记录」板块（与人生视图同版发布）

周 / 月 / 年三个维度。建议的呈现：

| 维度 | 主视图 | 说明 |
| --- | --- | --- |
| 周 | 每日横向条形，计划与实际叠加 | 一眼看出哪天超了 |
| 月 | 日历热力图 | 颜色深浅 = 当日工时 |
| 年 | 52 周条带 | 类似贡献图，密度即强度 |

关键指标，选真正有意义的、不要堆砌：

- 平均每日工时
- **加班总时长 / 加班占比**
- 最长连续工作天数
- **准点下班率**——实际下班 ≤ 计划下班的天数占比

最后这个是这个 App 独有的指标，也是最能驱动行为的一个。市面上的工时 App
统计的是"你干了多少"，这个统计的是"你有没有按时走"，和产品名字是一回事。

薪资相关的统计沿用现有的生物识别门禁。

## P1b — 人生视图（与记录同版发布）

**输入**（三个，都存本地）：出生日期、首次上班日期、目标退休年龄。

**核心视觉建议：人生周格图**——一格一周，横向 52 格，纵向若干年，覆盖从出生到
预期寿命。分区着色：童年 / 工作期 / 退休后，当前这一周高亮。

这个视图有个天然的、极漂亮的性质，正好化解 P0.2 里那个"真实还是推算"的张力：

> **过去的格子用真实记录着色，未来的格子用推算着色，两者视觉上本来就该不同。**
> 已经过去的人生是数据，还没到来的人生是估算——这不是妥协，这是这张图应该
> 表达的东西。

**衍生数字**：一生总时长、已工作时长、剩余工作时长、以及"真正属于自己的时间"
（扣除睡眠后的非工作清醒时间，睡眠按可调的默认值算，并明示这是假设）。

**分寸提醒**：这个视图很容易变成焦虑制造机。建议基调放在"还剩多少属于自己"
而不是"你已经卖掉了多少"，并且**不要**做推送提醒。

## P2 — 「待办」：番茄钟做减法（单独发布，最后）

你说不想做成市面上那种复杂度，我认为减法的关键是：**不要做一个通用番茄钟，
要做一个知道你几点下班的番茄钟。** 这是别人做不了的部分。

**与「接下来」合流**：待办不是独立列表，而是**填进今天剩余工作时间的内容**。
一个任务只有三个字段：标题、预估几个番茄、是否完成。没有项目、没有标签、
没有统计面板、没有优先级。

**排程规则**（这是差异点）：

- 番茄钟**不会跨过午休**，也**不会排到下班之后**
- 剩余时间放不下的任务，明确告诉用户"今天排不下了"，而不是让他自欺
- 下班时未完成的任务**静默顺延到明天**，不做任何愧疚感设计

**运行模型**：复用现有 `LiveActivityService` + `NotificationService`，
番茄钟以实时活动形式在灵动岛运行，和倒计时是同一套机制。
需要考虑二者在灵动岛上的**共存或互斥策略**——这是本板块最主要的技术未知数。

## 开放问题

已决的不再列（Android 路线、历史回填形态、付费边界、上线节奏见上方决策表）。
剩下这些还需要你定：

1. **买断用户的分界版本**：切换订阅的那一版版本号是多少？
   `originalAppVersion` 的比较需要一个明确的分界线，而且一旦发布就不能改。
2. **番茄钟与下班倒计时在灵动岛的共存**：同时只能有一个 Live Activity 比较合理，
   但"专注中"和"距离下班"用户可能都想看。番茄钟那一版才需要，但会影响那时的架构。
3. **预期寿命取值**：固定值、按地区统计值、还是让用户填？涉及口径与观感。
4. **Mac 端是否同步进这套**：CloudKit 私有库天然覆盖 Mac App Store 版本，
   但桌面端目前是 Tauri，不共享 SwiftData。要么 Mac 端只读、要么暂不参与。

## 交付顺序

```
P0  地基：上班实记 + CloudKit + StoreKit + 隐私文案/标签
P1  记录板块 + 人生视图        ← 同一版发布
P2  待办与番茄钟               ← 单独发布，最后
```

P0 与 P1 之间刻意留出时间差：**记录页需要有数据才有说服力**，
上线当天就是空白页的体验很糟。先让数据攒起来。

### 关于 P0 内部的风险集中

三件事挤在一个版本里，风险是叠加的：任何一个被审核卡住，另外两个都跟着延期。
而且这一版同时改变了**商业模式**、**隐私姿态**和**后台行为**——审核问询的概率
不低。

建议**把「上班实记」单独先发**：它零新界面、零外部依赖、不改隐私姿态，
是三件事里唯一一个「越早发收益越大」的。CloudKit 与 StoreKit 再一起或分两版跟上。
这样即使后两者被卡，数据已经在攒了。

顺序上仍然是三件地基都先于记录 UI，与你定的一致。
