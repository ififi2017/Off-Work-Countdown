# DoneAt Web 多语言工时与税前收入工具库实施方案

**版本：v3**  
**日期：2026-10-31，Asia/Taipei**  
**状态：实施规划，覆盖首发到完整目标；本文件不表示已开发或已上线。**  
**实施站点：off.rainif.com**  
**代码仓库：ififi2017/Off-Work-Countdown**

## 1. 项目定位与终极目标

建设 DoneAt 旗下可独立使用的多语言 Web 工具库，覆盖工资换算、班次工时、工作日期、排班比较、工作机会比较和经过审核的地区计薪解释。用户从搜索结果进入后，可以直接在网页获得答案、修改条件并完成计算。

本项目以自然搜索曝光和查询覆盖为主要目标。App 下载记录只辅助安排市场研究和内容投入；App 安装、原生端激活和订阅收入不作为本项目的验收指标。

### 1.1 已确定的实施边界

1. 工资、工作日期、排班等逻辑可以建立独立的 Web 算法体系，无须复用现有 App 的计薪或排班算法。
2. 新 Web 工具内部共用同一套明确的计算规则，避免同一口径在不同页面产生不同结果。
3. 实施范围包括 Web 算法、交互页面、内容、本地化、路由、搜索基础设施和运营维护。
4. 客户端改造、跨端算法同步、原生设置迁移、App 安装归因不在范围内。
5. 下载入口可以作为普通品牌导航保留，但不承担工具的主要操作，也不阻止用户在网页完成任务。
6. 用户输入的工资及其可反推金额的计算结果，不进入 URL、搜索元数据、埋点、服务端日志或分享内容。
7. 本方案替代 v2 中“必须复用 App 公式”“Web 与 App 地区默认一起迁移”“以安装转化决定页面价值”的要求。

### 1.2 完整目标的交付定义

完整目标分为能力交付与搜索成效两部分：

| 维度 | 完整交付目标 |
|---|---|
| 工具能力 | 完成第 4 节所列的通用核心工具、日期与排班能力、比较工具；地区特殊专题按审核状态发布 |
| 语言 | 现有 19 种语言均完成第 3.3 节的六项基础页面能力和语言审核 |
| 主要市场 | 下载分布前 20 个地区均有明确的支持方式：已审地区内容、适用通用工具或有理由的专题暂缓 |
| 已观察地区 | 对全部 54 个地区完成覆盖登记，用户都有可用的通用入口；不将其机械扩成 54 套网站 |
| 搜索基础 | 页面清单、导航、sitemap、canonical、hreflang 一致；用户和爬虫都能读取主要答案 |
| 长期维护 | 有规则与日历来源台账、内容复核责任、修订与合并页面流程 |
| 搜索成效 | 持续增加相关非品牌展示、查询与市场覆盖，以实际 Web 数据衡量 |

六项基础能力按 19 种语言规划，对应约 114 个页面入口，其中已有工具页可以计入，不重复建页。地区专题和独立问题页预计再增加约 20–60 个入口，完整阶段可按约 130–180 个可索引 URL 预留建设容量。

该区间用于预算与维护规划，不是流量承诺、搜索政策阈值或必须凑满的页面配额。发现重叠意图时允许合并；完成标准是能力与覆盖清单，而不是页面总数。

### 2.3 发布排序方法

按四项证据综合安排同一波次中的发布顺序，不建立未经校准的精确评分：

1. 已有 Web 查询、国家和页面展示，或可靠的关键词与搜索结果调研。
2. 页面能提供的独立答案和工具价值。
3. 规则来源、语言审核与持续维护的准备程度。
4. ASC 地区受众，作为研究线索及条件接近时的排序依据。

未知的搜索需求记录为“待验证”，不等同于零需求。新增页面不需要先证明能带来 App 安装。

### 3.3 每种语言的六项基础页面能力

完整阶段，19 种语言均提供以下六项能力：

1. 工具库目录：介绍可用工具，并提供可抓取的分类链接。
2. 通用税前工资换算：年、月、周、双周、半月、日、小时等周期转换。
3. 班次工时计算：上下班、跨午夜和休息时间；现有 work-hours-calculator 可复用或在 Web 内演进。
4. 日期区间工作日计算：用户自定周工作日，明确首尾是否计入；无官方日历时标明仅按周排班计算。
5. 实际工时对应收入：按同一期间的收入和工作量计算有效时薪。
6. 两份工作比较：比较税前收入、实际工时、工作天数与可选通勤投入。

这些页面不依赖当地复杂工资法规即可提供明确价值。当地法定参考、薪酬结构和特殊日历另行叠加。

### 3.4 全部 54 个地区的支持登记

所有地区至少登记：可用语言入口、可用通用工具、已审核地区专题、日历覆盖类型、待补来源及维护负责人。

“可用通用工具”允许用户填写自己的币种、工时、工作天数与收入，不能包装成已验证当地工资法规。只有确有内容差异和搜索价值时才建立独立地区 URL。

## 4. 完整工具与页面目录

页面家族决定内容覆盖，工具模块决定功能复用。以下清单是完整建设范围；页面可合并，不为每一种输入输出组合生成独立 URL。

| 家族 | 完整功能 | 主要问题意图 | 实施顺序 |
|---|---|---|---|
| 工资周期换算 | 月薪↔日薪、月薪↔时薪、时薪↔年薪、年薪↔月薪、周薪换算 | “月薪一天多少”“25 an hour a year” | 首发核心 |
| 发薪频率 | weekly、biweekly、semimonthly、monthly、fortnightly | 双周与半月的差别、每期税前参考额 | 首发与第二批 |
| 时间收入换算 | 每分钟、每秒、每工作日、每日历日；可选网页进度演示 | “一秒赚多少”“今天按进度折算多少” | 第二批 |
| 实际投入与机会比较 | 有效时薪、两份 offer、可选通勤时间、不同工时安排 | 工资更高是否意味着每小时更高 | 第二批 |
| 班次与休息 | 班次跨度、跨夜、分段工作、带薪/无薪休息、周工时 | 9–6 算几小时、夜班怎么扣午休 | 核心能力扩展 |
| 工作日期与排班 | 日期区间、月度/年度工作日、指定工作日数后的日期、单双休、大小周、自定义轮班 | 某月上几天班、两种工作制差多少小时 | 中期主线 |
| 收入结构与兼职 | 几薪、额外固定奖金、全年总收入、月均收入、pro rata | 13薪怎么折算、兼职比例工资 | 中期主线 |
| 地区解释与特殊专题 | CN 21.75、TW 30/240、KR 209、JP 所定工时，以及审核后的特殊薪酬结构 | 为什么用这个除数、适用于谁 | 地区分批 |

### 4.3 现有页面的使用方式

现有 996、9-to-5、9-to-6、night-shift、work-hours-calculator 保留已有 URL。为其增加适当的工具互链；若新版 Web 算法使工具能力更完整，可以在 Web 路径内升级。

不再额外创建一个只有默认班次不同、没有新解释或能力的近重复页面。夜班专题必须真正处理跨午夜、休息归属等问题；大小周专题必须处理周期锚点，而不是仅修改周工作天数。

## 5. 独立 Web 计算引擎

### 5.1 代码边界

建议建立仅由 Web 工具路由引用的 features/web-tools 模块：

| 子模块 | 职责 |
|---|---|
| domain | 纯计算函数、输入校验、精度、工时与日期 |
| markets | 地区默认、适用条件、来源、生效日期与版本 |
| calendars | 工作周、用户覆盖、官方日历包与覆盖状态 |
| catalog | 工具、页面、语言、发布状态和相关链接 |
| content | 经过审核的结构化文案、示例和解释 |
| components | 表单、结果、假设、来源、对比表 |
| analytics | 仅用于 Web 的受控匿名聚合事件 |

不要求 import 现有 lib/countdown.ts，也不向原生端新增规则消费关系。新页面可利用仓库已有的 Web 专用页面扩展机制；现有构建配置区分 Web 与其他目标。[S8]

实现时验证模块和页面只进入预期 Web 产物，并执行与实际变动范围对应的仓库检查。客户端功能实现和发版不列为本项目的交付依赖。

### 5.2 三种核心计算目的

| purpose | 输入与分母 | 输出标签 |
|---|---|---|
| annualized | 用户指定付薪小时、付薪周数、收入结构 | 按所选条件年化/周期换算 |
| worked-time | 同一期间收入 ÷ 同期实际或预计工作量 | 每实际工作小时收入 |
| jurisdiction-reference | 已审核规则适用的计薪天数或小时数 | 地区工资折算参考 |

日历日均摊作为明确的展示模式处理，使用所选年份或日期区间的真实日历天数。它不替代工作日或计薪参考分母。

每次计算结果应附带 calculationVersion、purpose、period、assumptions、roundingPolicy；使用地区规则时再附 basisId、appliesTo、effectiveFrom、reviewedAt 和 sourceUrls。

### 5.3 收入结构与周期转换

定义：

- M：基础月薪。
- P：年度基础薪资相当于几个月，可为 12、13、14、15 或用户自填的合理值。
- B：另外加入、尚未包含在基础收入中的年度现金奖金。
- A：本次计入的税前年收入。
- r：时薪。
- Hp：每周付薪小时。
- Wp：每年付薪周数。
- N：参考发薪次数。

通用计算：

~~~
月薪输入：A = M × P + B
时薪输入：A = r × Hp × Wp + B
月均收入 = A ÷ 12
平均每次发薪参考额 = A ÷ N
年化时薪 = 本次纳入计算的年度收入 ÷ 对应年度付薪小时
~~~

年薪输入必须说明金额是否已经包含奖金或额外薪资；已包含的部分不能再次加入。

P 与 N 分开存储。“13薪”和“每两周发薪26次”不是同一个参数。界面分别显示基础月薪、全年计入收入、月均收入和平均每期金额。

52周、26次双周、24次半月可以作为普通年化模型。若提供某一具体年份的发薪日历，则根据首次发薪日期与周期计数，不能固定把所有年份写成26次。

### 5.4 实际工时与休息

内部同时保留三个值：

~~~
在岗跨度 = 班次结束 - 班次开始
付薪小时 = 在岗跨度 - 不付薪休息
实际劳动小时 = 在岗跨度 - 全部休息
~~~

按时薪估算班次报酬使用付薪小时。实际劳动时间均摊使用实际劳动小时。固定月薪不会仅因调整午休长度就自动减少，变化的是相应的均摊时薪。

休息区间取并集，避免重叠扣除；休息超出班次或覆盖整个班次时给出明确校验结果。

仅输入钟点时，计算的是排班钟表时长。输入具体日期、地点时区并要求真实经过时间时，需要处理夏令时。结束与开始相同时不能静默认作24小时；跨日应有明确次日标志或日期。

### 5.5 精度与输入

- 中间步骤保留足够精度，最后展示时按币种和输出用途舍入。
- 不使用已四舍五入的显示结果继续做下一步换算。
- 普通年化模型保留 52/12 的精度；官方参考口径若使用特定数值，则按该口径保留。
- 支持相应语言的千位分隔、小数符号和数字输入；不得把“1,500”误读为1.5。
- 空值与0分开处理；负工资、非有限值、无效日期和零分母返回明确错误，不输出 NaN 或 Infinity。
- 对比较工具，两个方案的收入与工时必须对应同一期间，奖金采用一致的计入选择。
- 可选通勤时间单独标为“每小时投入时间对应收入”，不称为合同小时工资。

### 5.6 网页收入演示

可以在 Web 内提供实时金额进度，但必须给出输入与分摊规则。未输入真实班次时使用明确的“演示进度”；不声称实际到账或雇主已经结算。

每秒更新只在本地执行，不产生每秒服务端请求。该能力按网页需求安排，不承担安装引导任务。

## 6. 工作日期与日历体系

### 6.1 基础能力

完整阶段支持：

- 自选每周工作日。
- 指定日期区间、某月和某年的工作日/工时。
- 首尾日期是否计入的清晰选项。
- 单双休、大小周、周期轮班及锚点日期。
- 用户指定的额外工作日和休息日。
- 有正式数据的国家或地方公共假期参考。
- 从某日起增加指定工作日数后的日期。
- 适用时按真实发薪起日计算发薪日历。

以日历日期处理工作日，避免把用户日期错误转换成 UTC 后跨日。班次的实际经过时间另用带时区的时间模型。

### 6.2 日期优先级

默认判定顺序：

1. 用户明确覆盖。
2. 所选日历包的指定工作日或补班日。
3. 所选日历包的休息日。
4. 用户的一般每周排班或轮班模式。

中国大陆的年度日历须同时存储休息日期和补班日期。是否工作与是否付薪分开建模，工作日历不能自行决定所有雇佣合同的工资规则。

### 6.3 日历包数据结构

每个日历包至少包括：market、subdivision、year、calendarType、sourceUrls、publishedAt、reviewedAt、version、coverageStatus。

| coverageStatus | 含义 | 页面表述 |
|---|---|---|
| official-complete | 指定地区、年份、适用类型的正式数据已完整审校 | 标出日历名称、年份及适用范围 |
| schedule-only | 仅按用户每周排班或周期排班 | 明示未计入公共假期 |
| custom | 用户自行覆盖 | 明示采用自定义日历 |
| partial | 资料不完整 | 不给出“全年官方准确工作日”的承诺 |

未来年份尚未公布正式安排时，仍可使用 schedule-only；不猜测调休日期，也不发布冒充官方日历的年份页面。

### 6.4 日历来源与适用范围

| 地区 | 来源方向 | 适用范围说明 |
|---|---|---|
| CN | 国务院年度放假调休通知 | 包括补班日，允许用户按单位排班覆盖 |
| US | OPM 联邦假期 | 联邦雇员假期参考，不能代表全部私营企业 |
| TW | 人事行政总处及政府开放数据 | 政府行政机关办公日历；民企规则另行判断 |
| JP | 内阁府国民祝日资料与 CSV | 国民祝日参考，叠加用户自己的排班 |
| 其他地区 | 对应国家、地方政府或主管部门 | 明确行政区和使用对象，不默认全国所有岗位一致 |

美国和台湾来源各自有明确适用对象；日本提供官方祝日资料。[S20]、[S21]、[S22]

## 7. 地区默认与规则审核

### 7.1 三种发布状态

| 状态 | 允许发布的内容 |
|---|---|
| arithmetic-ready | 使用用户填写的工时、收入与奖金，提供纯算术估算 |
| reference-reviewed | 在适用条件明确、来源审核完成后，提供地区工资折算参考 |
| special-review | 特殊合同、津贴或过渡法规待审核；通用工具仍可用，专题不发布 |

算法未完成当地法规审核，不意味着整个语言或市场都不能上线。可以先提供有明确假设的通用工具，暂不显示“当地法定工资”结论。

### 7.2 重点市场的处理原则

| 市场 | 可先使用的模型 | 参考或特殊规则处理 |
|---|---|---|
| CN | 月薪、实际工作日/工时；奖金自填 | 21.75为计薪参考，20.67为制度月工作日；用途分开 |
| US | 用户可改的40小时、52个付薪周示例 | 2080不是所有岗位的实际年工作小时 |
| TW | 实际出勤均摊 | 30/240用于明示适用月薪制的工资折算参考 |
| HK | 用户工作天数和工时 | 22只能是示例；相关法定权益有平均工资规则 |
| DE | 用户周工时和薪酬结构 | 不默认所有岗位都含13薪 |
| JP | 用户平均所定工时或实际工作量 | 不强制给所有月薪者使用一个统一除数 |
| TR、RU、VN、ID、TH | 月薪/年薪与用户自填工时 | 不未经核实设置全国统一法定分母 |
| BR | 按用户实际合同工时换算 | 规则需版本化；近期工时改革过渡期不使用无日期的永久44/220默认 |
| KR | 用户实际工时均摊 | 209适用于相应正常工时及有薪周休条件 |
| IN | gross金额，年/月薪与工时 | 明确CTC不等于可直接换算的现金税前工资；不推算税后 |
| SA及其他阿拉伯语市场 | 税前周期换算 | 不将阿拉伯语用户统一描述为“到手等于税前” |
| ES、IT、PT、AT | 年收入、基础月薪、额外奖金分别输入 | 13/14次不必然等额；合同或集体协议决定适用结构 |
| FR | 用户工时或合同工作日 | 35小时模型与forfait jours分别处理；218不作通用日薪分母 |
| GB、CA、AU、NZ | 可编辑周工时和付薪周数 | 特有词汇、发薪频率及福利专题分别审校 |

CN、TW、KR、HK 的参考口径有相应官方资料；FR、AT 与 AU 的资料说明了重要适用边界。[S12]、[S13]、[S14]、[S15]、[S16]、[S17]、[S18]

截至本方案日期，巴西2026年10月16日公布的改革存在分阶段实施安排。因此BR市场可先做用户自填工时的工具，涉及法规的默认值和解释须记录生效日期，不自行推导过渡期工资除数。[S19]

### 7.3 来源台账

每项地区参考规则记录：规则名称、用途、工资组成、适用对象、排除情形、原始来源、生效日期、审核日期、下一次复核日期、维护人。

法定/合同参考优先使用主管部门、法律原文或适用集体协议。二手计算网站可用于发现问题，不能作为唯一依据。规则发生变化时更新版本和说明；旧年份日历保留对应版本。

## 8. URL、语言和市场架构

### 8.1 采用语言前缀加市场路径

新工资页尚处于规划阶段，统一采用以下结构：

| 类型 | 示例 |
|---|---|
| 工具总目录 | /en/tools |
| 通用工资工具 | /en/salary/global |
| 美国工资总页 | /en/salary/us |
| 美国时薪转年薪 | /en/salary/us/hourly-to-annual |
| 英国年薪转时薪 | /en/salary/gb/annual-to-hourly |
| 台湾月薪换算 | /zh-TW/salary/tw/monthly-to-daily |
| 加拿大法语工具 | /fr/salary/ca/annual-to-hourly |
| 巴西葡语工具 | /pt/salary/br/monthly-to-hourly |
| 葡萄牙葡语工具 | /pt/salary/pt/monthly-to-hourly |
| 工作日期工具 | /zh-CN/workdays/cn/date-range |
| 通用工作日期工具 | /en/workdays/global/date-range |

该结构沿用已存在的语言前缀，市场作为独立路径段，不必先引入/en-gb等新的顶层UI语言。hreflang=en-GB可以对应/en/salary/gb/...，URL不需要与hreflang代码逐字相同。[S2]

现有路由只识别既有语言前缀，因此沿用前缀可减少v2方案的路由调整范围。[S10] 新增既有19种以外的语言时，扩展Web内容入口与页面外壳，不自动扩大App语言任务。

### 8.2 分开的维度

- language：内容语言，例如en、fr、pt。
- market：计算市场，例如US、CA、BR。
- formatLocale：数字和货币显示，例如en-US、fr-CA、pt-BR。
- currency：用户选择的币种；切换币种不进行汇率换算。
- purpose：年化、实际工时或地区参考。
- contentLocale：发布文案的语言与地区组合，例如en-GB。

语言切换尽量保持市场和计算意图。市场切换可以保留输入，但要说明只是改变币种和假设，没有兑换金额。设备语言和时区只用于可关闭的建议，不自动确定雇佣地区。

### 8.3 页面注册表

每条页面记录至少包括：

~~~
pageId
toolId
language
market
purpose
canonicalPath
translationGroup
status: draft / reviewed / published / retired
calculationVersion
contentReviewedAt
sourcesReviewedAt
relatedPageIds
~~~

仅published条目进入公开导航、静态构建和sitemap。未完成内容优先不生成，避免批量空壳。

不按“19种语言 × 所有市场 × 所有slug”生成笛卡尔积。相同意图和无实质地区差异的页面优先共用。

### 8.4 canonical 与 hreflang

- 已有独立价值的页面自指canonical。
- 真正等价的语言/地区版本建立互相回链的hreflang集合，包括自身。
- 不把404、未发布页、noindex页或不同问题页当作alternate。
- 没有实质差异的同语言地区内容先不创建；需要去重时明确首选版本。
- x-default指向该意图对应的通用可用入口；不统一乱指首页。
- HTML和sitemap的hreflang选择一种作为主要实现即可；若两处都有，从同一注册表生成。Google说明多种实现方法等价，叠加没有额外搜索收益。[S2]、[S3]

## 9. 页面内容与搜索质量

### 9.1 页面结构

1. 标题和H1准确描述当前问题。
2. 首屏提供可读的直接答案和默认假设。
3. 表单与计算结果。
4. 与本问题有关的例子或对照表。
5. 公式、口径和适用范围。
6. 必要的来源与更新时间。
7. 相关工具和上级目录。

先满足当前问题，再引导探索其他工具。普通品牌或下载导航可以存在，但不覆盖计算结果。

### 9.2 静态内容与浏览器计算

默认答案、示例、公式、说明和内链预渲染为可读取的HTML。用户输入与交互计算在浏览器本地执行。

Google能够处理JavaScript页面，但仍存在抓取、渲染与索引环节；预渲染主要内容有助于减少对渲染过程的依赖。[S5] 页面不应在JavaScript执行前只剩空表单或加载骨架。

### 9.3 生成和本地化标准

- 通用工具使用结构化文案和示例模板，允许共用组件与公式。
- 每个独立页必须有对应问题的答案、假设和解释，不能只替换标题、币种或几个数字。
- 翻译审核同时检查术语、货币、数字格式、公式含义和使用场景。
- 阿拉伯语检查RTL布局，其他语言检查长文本、非西文数字和移动端显示。
- 国家默认值是建议或参考，不通过语言选择强行套用。
- 每页至少经过一次人工内容审核；AI翻译初稿不能直接等同于审校通过。

Google的规模化内容与doorway政策关注页面目的和用户价值，不提供固定安全页数。[S1] 本项目的数量规划不能替代逐页的发布条件。

### 9.4 关键词与固定金额页

每个候选页记录：目标问题、目标语言/市场、搜索结果形态、现有自有展示、独立价值、与已有页的重叠情况、资料来源和审核状态。

通用转换器使用通用标题；固定金额问题作为示例，或在有明确查询证据时成为独立页。公开编辑的固定数字例子可以进入标题或slug，不能来自用户的私密输入。

首批不建立按所有整数金额自动扩张的页面系统。

### 9.5 结构化数据

按页面真实内容选择合适的结构化数据，不为了富结果编造评分。WebApplication可以描述工具，但是否获得软件应用富结果仍取决于完整要求及搜索引擎判断。[S7]

FAQ内容可保留帮助用户；Google自2026年5月7日起已停止FAQ富结果展示，不将其列为增长收益。[S6]

### 9.6 国内访问与搜索入口

CN方向在发布前检查大陆网络可达性、首屏主要内容、外部资源依赖和百度侧的实际抓取/收录情况。海外中文曝光与大陆曝光分别看待。

先沿用off.rainif.com已有工具站点；本项目不同时承担域名迁移。若部署环境确有访问问题，单独安排交付方案，不把未经测试的可达性当作已经满足。

## 10. 隐私、性能与观测

### 10.1 本地计算

默认输入保留在当前页面内存。若提供“记住设置”，由用户明确启用，并能清除本地数据。

工资、奖金、结果金额及可反推工资的完整输入组合，不进入分析事件、URL、OG、搜索元数据、日志、错误上报或分享卡片。避免自动表单采集或会话回放将其带出页面。

分享入口仅分享工具、市场与经过编辑的公开示例。实时演示不调用服务端计时或每秒写入统计。

### 10.2 性能实现目标

- 工具说明和例子尽量静态输出。
- 计算模块按工具家族加载，不在每个页面打包所有语言和市场日历。
- 常用运算即时本地完成，长日期区间或大对比任务进行合理分段。
- 发布页面的基础加载与交互性能不明显劣化。
- 不因纯静态页面添加按访客IP进行的每次请求动态计算。
- 保留现有语言路径避免无效中间件调用的优化意图。[S10]

性能预算在第一个实现批次实测后冻结，不在未构建前声称达到具体Lighthouse分数。

### 10.3 统计分工

Search Console作为搜索展示、点击、查询、国家和索引状态的主要数据来源。[S4]

站内统计只补充工具使用、计算完成和相关工具点击。可以定义有限枚举：

~~~
web_tool_used
web_tool_calculated
web_tool_related_clicked
~~~

维度限于预注册的pageId、toolId、language、market、purpose与版本，不包含输入数值。现有埋点只有事件名称，若要增加维度须明确修改接收格式及白名单，不能仅在方案中写一个对象就认为已实现。[S11]

事件次数只称事件次数，不伪称独立用户数或完整会话漏斗。首期不为本项目引入用户身份或跨产品关联。

时间以实际项目启动日T0计算。以下是建设计划，不是排名或收录承诺。各阶段可分批发布，语言审核与工程并行。

| 阶段 | 时间参考 | 核心交付 | 可控完成条件 |
|---|---|---|---|

## 12. 搜索目标与复盘方式

### 12.1 主要指标

| 指标 | 用途 |
|---|---|
| 相关非品牌展示次数 | 主要增长指标 |

品牌排除词以DoneAt及明确品牌/域名为准，不能把“下班倒计时”“shift countdown”等通用功能词一概排除为品牌词。按相同筛选条件比较，避免不同国家或页面集合直接混算。

### 12.2 基线和管理目标

在T0记录启动前连续28天的相关非品牌曝光B0，并单独跟踪新工具页面集合N。不得把749次下载换算为曝光目标。

以下是启动时可采用的管理目标，需在第30天用实际基线校准，均非调研证明可达的流量预测：

| 时间 | 增长目标建议 | 覆盖目标建议 |
|---|---|---|
| 第90天 | 当B0足够稳定时，相关非品牌曝光较基线增长约50% | 至少5个目标市场、3个工具家族连续4周产生相关展示 |
| 第180天 | 当B0可比较时，相关非品牌曝光达到基线约2倍 | 至少10个目标市场形成连续展示，核心家族均有真实查询反馈 |

B0为0或样本极低时不使用倍数，第30天根据新页面实际表现设置绝对目标。季节性、原有页面变化和新增工具效果分开解释，不把全站增长全部归功于本项目。

不要求每个国家都达到相同比例，也不把所有页面被索引作为工程能保证的结果。

### 12.3 根据结果采取行动

| 现象 | 处理 |
|---|---|
| 页面不可抓取或意外noindex | 修复技术问题 |
| 多个相似页被合并为同一canonical | 检查重复意图，补充差异或合并 |
| 有展示但查询明显不相关 | 调整标题、解释和页面定位 |
| 有展示、少点击 | 结合具体查询和排名检查，不只看站级平均CTR |
| 有点击、少计算 | 改善默认输入、表单和答案布局 |
| 同一问题的多个页面互相分散表现 | 选择主页面，合并内容与链接 |
| 某地区或新问题持续出现展示 | 增加适用专题或语言内容 |
| 短期样本很少 | 延长观察；不按几天无点击直接判定没有需求 |

App安装率、客户端激活和付费不参与以上扩展或暂停条件。
