## 2026-10-01 · 本轮规划与用户确认

本计划沿用 019 的结构，编号保持 021。v0.3 以本轮 15 项回复和此前已确认规则为产品依据；旧讨论中的建议与本版冲突时以本版为准。用户确认产品方向不等于代码、平台能力或发布已验收。

**一直保持的底线**：自动应用默认关闭，不做首次强制二选一；关闭时只留参考，不改变现有实际工时／倒计时／汇总，支持多选批量确认。应用的是对应班次实际采用的上下班时间，不永久改循环排班；原计划保留为正常工时与加班的基准。

**本轮新增或定案**：早到先记录，延后询问，若等待期间已到计划上班时间则按“掐点上班”只留记录、不再额外问早到；晚到／未确认上班在计划开始后半小时问一次，选择“今天休息”或“继续记录”；非工作时段确认加班从检测到达时开始（14:00 到、14:30 确认仍从 14:00 算）；同一天加班不拆成两个汇总项目，但保留真实分段与空档；不做家的地址；日历名称用“定位认证”；最小来源摘要可随正式记录同步到用户的 iCloud；自动化归现有 Plus；可分批交付并加入 Siri 能力研究与实现。

**前两轮已确认**：工作时段临时外出只留痕，不自动结束、不额外扣时；原午休扣除规则不变。非工作时段到访提醒默认 30 分钟，可选 15／30／60 分钟，同一到访最多问一次，未回应只留参考、不开始加班。

本轮没有再次询问已经决定的产品项。早到询问等待时长未单独指定，先复用上述停留提醒设置（默认 30 分钟）作为**实现默认**；几何半径、最大事件年龄等仍需 P0 实测后调整。用户“半小时后推送”明确落实为计划上班后 30 分钟的状态询问，不再保留 15 分钟默认。

v0.2 的单／多条复核、隐私、写入和平台约束继续保留。三个工程前提仍成立：**不能承诺任意后台定时执行；系统回收不等于用户强制退出；不能把既有倒计时按钮方法直接当成完整的上下班记录接口。** Siri 建议也不是定位事件或可靠后台调度器。

## 1. 与现有规定和实现的关系

### 现状

iOS 由原生 Swift 规则生成班次、有效工作段、提醒和汇总；Android 已有 Kotlin 原生工程与独立的领域层。共有行为仍受 TS／Swift／Kotlin 差分约束，iOS 文案以 String Catalog 为源，Android 资源由现有脚本生成。本功能不恢复 JavaScriptCore，不新增另一套薪资、排班或收入计算器。[R1][R2][R3]

已核对的 iOS `ShiftSessionStore` 可以脱离应用 Scene 执行，但其命令含义不同：[R4]

- `startCountdown(...)` 启动或武装现有倒计时，不能直接等同于“从此刻开始计算实际工时”。
- `stopCountdown(...)` 在 `session.followsSchedule` 时直接返回 `false`，不能用它实现所有排班模式的自动下班。
- `clockInEarly(...)`、`clockOffEarly(...)`、撤销、当日覆盖与工作观测已有各自的规则和写入流程。提前上班保留现有分钟取整；不能由定位层重新规定精度。
- 工作观测目前受既有权益规则约束；本次 Plus 自动化需在统一权益层明确新增采集、自动应用与历史复核／纠错的不同能力。不能在定位层绕开 `shouldCollectObservations`，也不能把“无新增观测权限”显示成“已保存实际记录”；需要调整历史复核例外时按 §3.14 同版更新规则与测试。

Android 的读取入口为 `ShiftSession`，写入通过 `SessionCommands` 与 `SessionStore.run`；业务库采用原子 JSON 文件，不是 Room。运行会话与业务归档分离，本功能必须延续该边界。[R3]

### 契约

- 新建的是**事件适配器、自动化决策层与统一班次命令**，不是另一套计时系统。
- 手机上的自动事件、快捷指令、通知操作和人工操作最终进入同一业务写入边界。禁止在定位回调、Receiver、Intent 或 View 内直接修改记录文件。
- 保留 `segments + plannedEndAtMs + overtimeEndAtMs` 语义；不把工作时长改成 `结束 - 开始`，不把到达延迟变成顺延下班。仅仅仍在公司不证明加班；正常班次有效晚离开按 §3.9 形成加班结果，再由自动应用／人工复核策略决定是否记入实际工时。
- Android 的 021 增量需更新 feature parity／规则测试与 `docs/android/progress.md`；不静默追随 `main`，不重开已确认的收费、备份或 Wear OS 决策。
- iOS 新 UI 延续原生设计与 `OWCDesign`／`OWCMotion`；Android 延续稳定 Compose／Material3 与现有设计 token。不得为了本功能换 UI 框架或引入实验性组件。
- 新增隐私边界、数据格式或跨端规则时，在同一个 PR 更新相关工程规范／ADR／测试，不出现实现与文档相互禁止的中间状态。

## 2. 方案选择与能力边界

### 首版与后续范围

| 路线 | iOS | Android | 本计划定位 |
|---|---|---|---|
| 原生地理围栏 | `CLMonitor` + 授权会话 | `GeofencingClient` + `PendingIntent` | 双端原生自动化主路线，分别通过真机及发布门禁 |
| 快捷指令 → 自动化事件 | App Intents；到达／离开、专注模式等由系统快捷指令触发 | 无需强行实现 iOS 快捷指令的等价产品 | iOS 可独立交付的低权限路线，默认只记录 |
| Siri／系统建议 | App Shortcuts、查询结果、交互捐赠及 PredictableIntent；适配版本支持的结果卡片 | 不以 Siri 为双端公共依赖 | iOS 附加入口，不能替代围栏／本地通知；见 I4 |
| 围栏 + 当前 Wi-Fi | 可执行时读取，满足系统权限条件 | 可执行时读取，按系统版本处理权限与字段脱敏 | 后续可选增强，不能成为保活方案 |
| Wi-Fi 单独监听 | 不作为普通 App 的持续后台唤醒机制 | 网络回调不等于进程死亡后仍可持续接收 | 不作为首版主路线 |
| iBeacon／BLE | 可另行验证 Core Location Beacon 条件 | 需独立验证 BLE 扫描与后台限制 | 后续硬件方案，不承诺楼层级可靠识别 |
| NFC／系统自动化／第三方自动化 | 可借用已公开的班次动作 | 后续评估安全的用户触发入口 | 可选辅助，不属于“无操作自动到离岗” |
| 高频定位、长期前台服务、定时轮询 | 不采用 | 不采用 | 不以电量、常驻通知或后台权限换取虚假的可靠性 |

原生主路线是系统区域事件，不保证秒级触发。Android 官方明确说明后台事件可能有分钟级延迟；Wi-Fi、网络定位和设备环境会影响交付。Google Play services 不可用的设备不能被当作已支持该路线。[A4][A5]

### 必须修正的实现假设

1. **不得实现“后台 `sleep(180)` 后确认到达”。** iOS 不提供任意时刻可靠运行应用代码的通用机制；`Task.sleep`、`Timer`、后台刷新、静默推送或本地通知都不能补成这样的保证。有限后台执行时间只用于完成当前事务。[A3]
2. **Android 的 `DWELL` 与 iOS 的圆形条件不是同一个能力。** Android 可交给系统执行停留判定；iOS 首版使用空间防抖与业务过滤，不展示未经验证的“停留三分钟自动确认”选项。[A1][A4][A5]
3. **系统回收和用户强制退出分别处理。** 合法授权与会话恢复可使 iOS 在系统回收后继续接收事件，但不能承诺用户划掉 App 后仍能自动工作。Android 强行停止、权限撤销及厂商限制也需独立测试，不写“永不漏记”。[A2][A3]
4. **事件代表系统观察，不代表穿过办公室门的准确时刻。** 原始事件时间、收到时间、执行时间必须区分；不机械减去三分钟来伪造“真实到达”。
5. **Wi-Fi 不使用随意的置信度分数。** 不采用“围栏 60 分 + Wi-Fi 40 分 = 100% 到岗”。规则必须可解释、可测试；SSID 匹配只证明当前网络条件，不证明人在工作。
6. **不作零网络依赖承诺。** 班次决策与存储本地执行，不需要 DoneAt 服务器；但系统定位、Google Play services 和选点地图可能依赖其服务及网络。[A4]

## 3. 产品与跨平台业务契约

### 3.1 开启方式与配置

入口为 **设置 → 自动化 → 工作地点自动化**。整体监控默认关闭；升级、恢复备份、同步偏好或安装到其他设备，不自动开启。监控开关和“自动应用检测到的上下班时间”是两个不同设置；关闭后者不停止检测和记录。新增自动化采集与自动应用属于现有 Plus，历史处理边界见 §3.14。

| 项目 | 已确认规则／未单独指定的实现默认 |
|---|---|
| 工作地点数量 | 最多保存 5 个；逐个启停；停用仍占已保存名额；共同使用现有排班，不产生五份收入 |
| 自动应用开关 | `applyAutomationTimesAutomatically = false`；主动开启后，有效正常到离岗结果可自动采用，早到／额外到访的明确开工确认不被绕过 |
| 未开启自动应用 | 设置中的自动化记录保存待复核建议；不改变实际记录、当班计算或汇总；支持单条／多选批量确认 |
| 首次体验 | 不强制二选一，不把定位授权视为同意自动改工时 |
| 正常到离岗通知 | 按用户通知设置提交，表达“已记录待复核”或“已应用”；检测与通知独立 |
| 到达／离开区域 | 实现默认内圈 200 米、外圈增加 100 米，可调整，P0 实测；不是精度承诺 |
| 正常到达匹配窗口 | 实现默认计划开始前 120 分钟至后 180 分钟且唯一匹配班次；窗口只作匹配，不自动把早到算工时 |
| 正常离开 | 计划结束前只作临时外出／候选，明确提前结束须人工；计划结束及之后的有效离开生成下班／加班建议 |
| 最大自动延续窗口 | 实现默认计划结束后 6 小时；超限转待复核而不是截断用户真正工作或按原计划静默结算 |
| 早到询问 | 先记到达，再延后询问；实现默认复用停留阈值 30 分钟，可选 15／30／60；若询问时刻不早于计划开始则不安排额外早到询问 |
| 掐点到岗 | 等待窗口内跨到计划开始，或用户已明确开工：仅保留到达记录和正常通知，不再问早到，不自动增加提前加班 |
| 非工作时段到访提醒 | 已确认默认 30 分钟，可选 15／30／60；同次到访最多问一次；未响应不开始加班 |
| 上班状态询问 | 已确认计划开始后 30 分钟，每班最多一次；晚到或尚未确认状态时用对应中性文案，继续记录不等于确认应用 |
| 临时外出 | 工作时段内只留痕、不中断、不额外扣时，原午休规则保持；返回不重复开班 |
| 多地点转场 | 正常工作时段沿用临时外出；计划结束后须明确继续工作／工作转场，否则空档待复核 |
| 当日状态 | 正常、外勤、出差、居家、休息；支持今天／指定日期范围，不新建“家”的地址字段或围栏 |
| 日历标识 | 使用“定位认证”；只表达已采用时间边界的位置证据，支持部分认证与历史认证 |
| 保留／同步 | 未采用参考 90 天；已采用的最小溯源随正式记录保留，并可随用户开启的私人 iCloud 同步／备份迁移 |
| 人工优先 | 人工更正、休息选择、撤销不被后续自动事件覆盖；按班次身份抑制，不在午夜重置 |

“自动应用”不绕过唯一班次、事件时效、文件保护、人工修改或版本冲突。不合格结果进入待复核并说明原因；“定位认证”的高质量门槛另行检查，不因自动应用或 Plus 身份而提高。

切换开关只影响之后提交的自动决策，不批量应用积压参考、不回滚已采用记录。提交时重读开关；关闭后旧自动写入队列转待复核。手工确认本身是明确授权，不能因自动应用开关关闭而禁止单条／批量采用。

### 3.2 班次匹配与计划／实际分离

- 通过现有排班规则解析工作日、手工改班、节假日、请假、跨夜与时区。定位不改变地区、节假日模板或未来排班。
- 排班模式按既有展开结果产生稳定 `shiftKey`，包含班次锚点与计划身份；跨夜 22:00–06:00 的离开属于前一天开始的班次。
- 无排班的手动模式，必须先明确选定现有班次模板、有效星期和触发时段，才可开启自动开始。未配置时保留人工／快捷指令明确启动入口，不自动猜测每天都上班。
- 存在多个候选班次、全天请假、休息日无手动安排、当前已有另一班次或输入无效时，不强行开始；给出中性的未执行原因。
- **默认按原计划结束，不因晚到顺延。** 09:10 被识别到达、计划 18:00 下班，仍使用计划 18:00；检测时间作为观测时间保留，不把模板改成 09:10–18:10。
- 早到先记录并按 §3.9 的等待／掐点规则询问；确认“已到公司”只证明用户声明到达，只有明确确认“已开始工作”才采用提前开始及相应提前加班。自动应用开关不把早到自动变成开工。
- 自动记录来源不得凌驾于人工修正、请假与现有实际记录优先级。自动事件只补充自己的观测，不覆盖人工编辑的起止时间。
- 到计划结束仍在公司，不立即证明已发生多少加班；自动化继续等待有效结束事件。正常班次的有效晚离开按 §3.9 生成加班候选；开启自动应用时写入，未开启时保留参考等待确认。

计划、检测、采用必须分层：`PlannedShift` 保留排班；`WorkObservation` 保存传感器／用户声明；`WorkTimeProposal` 保存可复核建议；`AppliedWorkRecord` 保存最终采用值及证据引用。记录事件不等于应用时间，通知被展示／点击不等于用户已经确认。

“只记录”不能通过提前结束首页倒计时、改变当日覆盖或收入投影间接修改正式结果。明确点击确认后才进入同一实际工时写入路径。原计划下班基准不因为迟到、晚离开或采用记录而顺延，保持可用于判断加班。

### 3.3 统一命令，而不是直接包裹按钮

新增明确的语义入口，名称可按工程风格调整，但契约必须保持：

```text
startShiftFromAutomation(commandID, shiftKey, effectiveAt, source)
endShiftFromAutomation(commandID, boundShiftKey, effectiveAt, source)
undoAutomationCommand(commandID, expectedRecordRevision)
pauseAutomationForShift(shiftKey)
recordAutomationObservation(eventEnvelope)
buildWorkTimeProposal(eventIDs, shiftKey, rulesVersion)
applyReviewedProposals(batchID, selections, expectedRecordRevisions)
confirmAdditionalWork(visitID, chosenStartAt, expectedRevision)
confirmEarlyWork(visitID, shiftKey, chosenStartAt, expectedRevision)
continueRecording(shiftKey, expectedContextRevision)
setDayWorkContext(shiftKey, context, expectedRevision)
setWorkContextRange(startAnchorDay, endAnchorDay, context, expectedRevision)
getShiftStatus(at, accessContext)  // 只读，供 App／Siri 共用无薪资投影
```

这些是**拟新增的业务接口**，不是仓库已有函数。调用只携带班次身份、时间和来源，不携带薪资、原始坐标或 SSID。

- iOS 由 `ShiftSessionStore`／既有记录命令队列实现；Android 由 `SessionCommands` 经 `SessionStore.run` 实现。
- 自动开始须明确区分“倒计时已经按排班武装”“检测事件已保存”和“实际时间已应用”。未开启自动应用时只记录事件／建议；重复启动不重设时间、不重复观测。
- 自动结束区分手动计时、排班内提前结束、已按计划完成、已人工结束及已声明加班。不能把所有情况都调用 `stopCountdown`，也不能将所有离开都记为“提前下班”。
- 不调用 `force=true` 绕过休息日／请假；不通过永久修改 `startMinutes`／`endMinutes` 达成一次自动操作。
- 业务写入成功后，再生成 Widget、Watch、提醒、通知与已存在实时活动的更新需求；后台不播放庆祝、不弹评分、不导航到页面。
- 返回结构化结果：`recordedForReview`、`applied`、`alreadyApplied`、`ignored(reason)`、`needsReview(reason)`、`temporarilyUnavailable(reason)`。保存参考只能显示“已记录待复核”，不能显示“已更新工时”；未成功持久化不得显示已保存。
- 记录、当日覆盖、会话状态与 Focus 的关联行为沿用既有规则。UI 层不能自行补算工时或绕过权益门禁。

### 3.4 事件模型与状态机

持久化的自动化状态是业务处理进度，**不是另造一份声称实时准确的位置状态**。iOS 的系统观察以 `CLMonitor` 记录和收到的事件为准，不能把多小时前的 `lastEvent` 当成刚采样的位置。[A1]

| 当前状态／输入 | 决策 |
|---|---|
| 新建地点、重新授权、重装恢复后首次状态 | 只建立基线；人在公司时可明确选择“现在开始”，不伪造刚刚到达 |
| `idle` + 新的有效内圈进入 | 保存事件，检查时段／班次／人工抑制；生成建议，按自动应用开关决定提交或待复核 |
| `candidate` + Android 有效 `DWELL` | 早到先校验是否已到计划开始／已开工；非工作时段只问开工，普通到岗才按开关处理；不将过期 ENTER 补成成功 |
| `candidate` + 离开／权限失效 | 不自动生成完整工作记录；保留必要参考及未采用原因 |
| `bound` + 内外圈之间移动 | 保持当前班次，不重复开始或结束 |
| `bound` + 新的有效外圈离开 | 保存离开；结合其他地点和模式判定，按自动应用开关处理，不结束另一班次 |
| `bound` + 计划结束前离开（含午休） | 临时外出不结束、不额外扣时；不回公司时可供人工确认提前下班，不承诺定时自动倒推 |
| `closed` + 同一班次的重复事件 | 不重复结束、不自动重开；新到访须显式确认额外工作，新增真实段但合并当日汇总；旧班次事件不能操作新班次 |
| 人工修改／结束／撤销 | 人工优先；取消旧候选和建议，建立当前班次抑制 |
| 位置未知、超时、读不到 Wi-Fi、权限变化 | 更新可用性，不生成“离开”事实；保留已存在班次 |

计划倒计时完成与自动化等待实际结束是不同生命周期：到原计划下班时不能清除绑定、注销地点或丢掉后续 EXIT；保留等待结束证据的状态，直到有效离开、用户结束／休息、明确失效或异常转待复核。如提供 `autoStart`／`autoEnd`，两者仍受自动应用总开关控制，不能绕过仅参考模式。`bound` 可仅代表参考事件已关联计划班次，不代表已开工或已应用。无班次绑定的 EXIT 可保留独立检测参考，但不能凭空生成完整上下班记录；仅自动结束时需明确绑定用户已开始的班次。

### 3.5 防误触发与后台延迟

首版采用**内圈进入／外圈离开 + 时段过滤 + 班次绑定 + 幂等 + 人工优先**。这是产品防抖策略，不是系统原生精确门禁能力；路过公司、定位漂移、临时外出仍可能误判。

- Android 的停留确认交给系统 `DWELL`。iOS 不用内存倒计时伪造相同能力，不长期持有位置更新来等三分钟。
- 首版不提供双端通用“离开五分钟后必定结束”。后续若增加 `pendingExit`，必须持久化候选，并由新的有效证据／人工确认推进；WorkManager 或 iOS 后台刷新只能提供机会性执行，不作为准点闹钟。
- 若开启更严格的二次确认，无法获得新证据时保持待确认，不能把“没有收到反向事件”当作持续在内／在外的证明。
- 短时到离岗可标记为“请核对”，不静默删除已经提交或用户修正过的记录。
- 无人工确认的自动处理建议设置 15 分钟最大事件年龄，超限只生成核对建议。无可信观察时间时保留空值，收到时间仅作为带说明的建议依据，不能据此证明事件新鲜并绕过保护。用户仍可查看、修正后明确采用。
- 不按回调顺序盲目改变记录。批量／重放事件先校验配置代次、班次、时间与已处理身份；旧 EXIT 不得结束刚开始的新班次。

### 3.6 幂等、写入和撤销

- 事件接收先持久化最小命令信封，再提交业务命令，最后记录结果。业务写入必须能以稳定 `commandID` 查重；仅在内存去重或每次重试生成随机 UUID 不合格。
- 自动化元数据和业务归档若不能单事务提交，应采用持久化命令日志 + 业务侧命令回执，覆盖“业务已保存但日志未更新”的崩溃窗口。
- 同一次动作从原生事件、快捷指令和用户按钮并发进入时，除命令 ID 外还要按当前班次状态拒绝重复操作。不能仅靠事件 UUID 不同就认为是两次上班。
- 执行前重新读取当前归档版本与权限状态；旧快照不得覆盖 CloudKit 合并或用户刚完成的编辑。
- 撤销是带版本检查的补偿命令，只撤销本次自动写入及其派生结果。若用户随后修改记录，转入编辑确认，不恢复整份旧数据库。
- 自动操作被撤销后抑制当前班次自动重做；保留“恢复自动化”入口。批量操作对每条实际成功应用的记录保留独立命令回执及共同 batchID；重试不重复应用，不能把部分成功报告为全部成功。
- 损坏归档、写入失败或受保护数据不可读时，不发布成功状态，不覆盖原文件，不绕过已有隔离机制。

### 3.7 时间、隐私、iCloud 与多设备边界

- 使用既有记录／班次时区解析日期、跨夜与夏令时。自动事件保存绝对时间；跨夜班次按原班次锚点归属，不用午夜切断加班。
- `observedAt` 是系统观察时间，未知则留空；`receivedAt`、`processedAt`、`appliedAt` 分别保留。用户选定的实际时间不覆盖原始时间，不机械扣除系统延迟。
- 不保存连续轨迹。地点名称、坐标、半径、SSID、注册代次、原始事件、设备监控开关、未采用建议和执行队列放在本机专用存储，不加入会同步的普通偏好。
- 未采用参考及其最小可读详情保留 **90 天**；到期可清理，复核页明确显示保留期限。短期原始诊断实现默认最多 7 天／200 条；不能因清理诊断而让仍在 90 天内的参考变成无法解释的记录。
- 已采用记录的最小来源摘要随正式工作记录保留，直到用户删除。采用前事务性拷贝必要摘要，不依赖以后仍存在的本机事件日志。

**已确认：最小溯源可同步到 iCloud。** 通过项目既有、用户主动启用的私人 CloudKit 同步通道扩展，不新增 DoneAt 账号或公开数据库；同步设置未开启时仍只存本地。批准的是正式工作记录及其最小来源摘要的同步，不是把坐标、SSID、设备围栏或原始日志上传。C1 先核对既有 CloudKit 与隐私批准范围；若该类正式工作记录尚未进入现有同步，本次需连同其父记录一起设计同步及迁移，不能只传孤立来源，也不能假称现有代码已经支持。[R1]

| 数据 | 本机 | iCloud／业务备份 |
|---|---|---|
| 正式上下班时间、实际有效工作段、当日加班汇总所需业务数据 | 保留 | 按现有用户同步／备份设置处理 |
| 已采用的最小来源摘要 | 保留 | 本轮批准可同步／导出：来源类型、观察／收到／采用时间、采用方式、修改链、规则版本、证据等级与其依据摘要 |
| 公司名称、坐标、SSID／BSSID、围栏标识、原始定位载荷 | 按监控需求本机保留 | 不进入本计划的同步／导出 |
| 90 天未采用参考、诊断、待执行命令、Siri 捐赠 ID | 本机 | 不同步、不随设备迁移自动执行；后续扩展需另有授权 |
| 自动化启用、设备授权、注册状态 | 本机重新确认 | 不同步成另一台设备的有效授权 |

本机敏感配置／原始日志目录需落实 iOS 系统备份排除与 Android 既有备份 include-list／`noBackupFilesDir`，不能只因未写 CloudKit 就声称不随整机备份上传。iOS 备份排除配置在 P0／C1 核对可用 API 并检查最终产物。

同步条目使用跨设备稳定的业务 ID、修改链、规则版本与删除墓碑。iCloud 回放是数据合并，不是一次新的到岗／开工事件；不能重新通知、注册围栏、增加工时、再次捐赠 Siri 动作或覆盖已更新人工记录。云端旧版本／缺失来源返回 `unknown`，不默认为认证。修改双方冲突按统一记录合并流程处理，不把时间戳最大的一方无条件当真。

恢复设备显示“定位认证 · 历史来源”，允许查看原始方法与采用过程，但不声称新设备重新验真。不存在原始坐标时仍可展示已有最小摘要；删除正式证据时标识降级。账户退出／切换不得把上一 iCloud 账户的待上传数据送到下一账户；离线重试与删除传播需验收。

需审计当前 `RecordJSON`、CloudKit payload 和旧客户端行为，必要时正式升级 schema，并同步 iOS／Android 导入兼容；Android 本轮不新增 iCloud 登录或自动跨平台云同步。未知字段不能被旧客户端静默丢失后再回写覆盖，新版变更发布前给出兼容／迁移方案。

首版由一台随身主设备负责检测；iPad、Mac 或第二台手机接收同步不等于接管检测。用户在多个设备分别开启时不承诺离线跨设备“恰好一次”，必须提示并遵守现有冲突处理。Siri 在非执行设备读取快照要说明数据时效，不能把只读入口变成远程自动开班。

删除地点时注销条件并删除配置，正式工时和最小溯源保留。仅关闭监控时保留用户保存的地点供以后开启，但不继续检测；提供独立删除入口。关闭监控、关闭自动应用与清空参考是不同动作，不能互相隐式代办。用户明确删除证据后不得保留无法解释的完整认证。

### 3.8 到离岗通知与设置记录

有效到达／离开先保存事件，再按通知设置提交**本地通知**，不新增远程推送服务器。系统通知权限、专注模式与交付策略意味着只能证明已提交，不能证明已展示／已读。[A3][A15]

| 场景 | 通知及行为 |
|---|---|
| 正常到达／离开，仅参考 | “已记录到达／离开时间，可查看并复核”，不声称工时已改变 |
| 自动采用成功 | “已更新本次上班／下班时间”，提供查看／撤销；提交失败不报成功 |
| 早到且等待后仍在计划开始之前、未明确开工 | “已经到公司并开始工作了吗？”；选择“已开始工作”或“只是提前到达”；存在不确定性时文案不能声称刚重新定位 |
| 早到等待期间已到计划开始或已明确开工 | 不发额外早到询问；已有到达记录和按设置的正常通知保留，不将掐点当提前加班 |
| 晚到或尚未确认，达到计划开始后 30 分钟 | “今天按正常上班记录吗？”／“今天开始上班了吗？”；进入 App 选择“今天休息”或“继续记录”，亦可设置外勤／出差／居家 |
| 工作时段临时外出 | “检测到暂时离开工作地点，当前班次继续”；可进入 App 明确提前结束；不扣临时外出工时 |
| 临时外出返回 | “已记录返回，继续当前班次”，不重复生成上班记录 |
| 正常班次晚离开 | 明确下班时间、当日加班建议为待复核或已应用，不显示工资 |
| 非工作时段额外到访达到阈值 | “这次到访需要记录为加班吗？”；确认默认从检测到达时起，不响应不开始 |
| 计划结束仍缺有效结束／提前离开后没返回 | 至多一次中性核对机会；不推断已经下班、未工作或无限加班 |
| 人工修正冲突 | 保留人工值，提示可核对，不自动覆盖 |

到达、离开和中途返回可分类关闭通知；关闭通知不停止已启用的检测／记录。午间同一有效离开／返回各最多通知一次；双圈、重叠地点、重投递不能刷屏。“检测成功”与“应用成功”合并，不为同一边界连发两条。

早到询问、额外开工询问和上班状态询问共用按 `visitID/shiftKey` 管理的通知注册表，但保留不同目的。已询问并确认早开工，不再邀请同一时段“额外加班”；同一次晚到既有未到岗询问又有到达回调时，只更新当前状态，不重复询问。**待复核不等于未到岗；已检测到达不等于已人工确认今日状态。**

默认正文不含公司名称、地址、SSID 或薪资。通知 action 只携带去敏记录 ID，执行时重新读最新班次、版本、有效期、开关和权益。打开通知、选择“继续记录”、忽略通知都不等于批准批量应用；只有明确的采用／开始工作／休息操作才产生对应业务变更。

iOS 早到询问在接收事件时可判断的 `dueAt >= plannedStartAt` 情况下**根本不预排**，不靠在上班时刻后台醒来取消。对已预排而后来状态变化的询问，取得执行机会时尽力取消，点击时再次校验；不能保证系统展示前最后一刻总能删除。[A3][A15]

### 3.9 早到、晚下班与非工作时段加班

#### 早到：先记录，延后询问；掐点不多问

设计划开始 `S`、有效到达观察时刻 `A`、早到等待时长 `D`，询问目标时刻 `Q=A+D`。`D` 的具体数值本轮未单独指定，首版复用已确认的停留设置（默认 30 分钟，可选 15／30／60）作为实现默认。

1. `A < S`：立即保存到达，正常到达通知按设置处理，不自动增加计划前工时。
2. `Q >= S`（含恰好等于）：视为等待期间已进入正常上班，即用户所说的“掐点上班”；只留记录，不安排额外早到／提前加班询问。不能因为保存的是 08:50 就在 09:00 自动应用成提前加班。
3. `Q < S`：可安排一次早到询问。若已离开、用户已明确开工／选择休息或事件已失效，则取消／不再执行。计划开始跨过了提醒的实际处理时刻，也只留参考，不补发过期早到询问。
4. “已到公司／只是提前到达”仅确认到达，不代表工作；用户明确确认“已开始工作”时默认从检测到达时刻采用，可主动修改。计划前有效段记为提前加班，和当天其他加班合并展示。
5. 未响应维持原规则，达到计划时间后按原排班运行；开关关闭时检测始终只是参考。iOS 询问不声称已连续定位验证整个等待时段。[A3][A15]

示例：09:00 上班，08:20 到，30 分钟阈值对应 08:50 可询问；08:50 到，阈值会落在 09:20，故不额外询问，保留 08:50 检测但不默认为 10 分钟提前加班。08:30 到且阈值恰在 09:00，同样不询问。

#### 晚到：正常工时与计划基准不混淆

保存晚到检测，正常结果按自动应用开关采用或待复核；采用后正常工时从所采用的实际开始算，计划结束不顺延。计划开始后 30 分钟的中性工作状态询问见 §3.10；“继续记录”不额外批准改时间，不回填为计划开始，更不能静默推断旷工、扣薪。

#### 正常班次晚离开

已开工且计划结束后发生有效离开：**晚于原计划下班的有效工作部分归入加班**。自动应用开启时采用，关闭时保存含加班的建议，明确复核后再影响正式汇总。达到计划结束但尚无有效结束事件时，首页倒计时正常结束并显示“等待下班记录”；可显示明确标注的估算值，但不把它写成已确认／已认证工时。

```text
正常班次延续加班 = 已采用的有效工作段 ∩ [原计划结束, 采用的实际结束)
当日加班总计 = 该归属日下已采用提前／延续／额外加班段并集的有效时长
```

既有 `segments` 规则仍负责休息扣除、重叠去重、时间与收入；UI 不自行计算“最后离开减计划下班”。不新增法定认定、公司审批或薪资倍数。没有“满半小时才计”或未经确认的整半小时取整，提醒门槛不是计费门槛。

例：计划 09:00–18:00、休息 12:00–13:00，采用 09:06–19:20：正常 7 小时 54 分，加班 1 小时 20 分，总有效工时 9 小时 14 分；晚到 6 分不抵消加班，也不把计划结束改成 18:06。

#### 非工作时段到访：确认从到达开始

休息日、结束后再次到访、无匹配正常班次的非工作时段，到达先留参考，默认停留 30 分钟后问一次（15／30／60 可选），未响应不开始。自动应用开关不绕过额外开工的人工确认。正常班次自然延续不再次邀请开工；早到由前述掐点规则优先处理。

**已确认默认起点是检测到达时间，不是推送／点击时间。** 14:00 到、14:30 确认，就从 14:00 开始；从现在／自定义是用户主动改选而非默认。明确“开始加班”是人工授权，即使自动应用关闭，也可应用这一条明确选择的工作段，但不能顺带采用其他待复核记录。

Android 使用系统 DWELL，仍可能延迟；iOS 使用询问型本地通知并尽力取消，不声称通知时重新证明用户还在公司。[A4][A15] 用户迟些才处理且已离开，转为补记已结束工作段，不启动一个错误的进行中班次；没有可信起点则要求核对，不凭回调收到时间伪造 14:00。

#### 同一天汇总一条加班，明细保留真实情况

**用户要求的是汇总不拆，不是把空档算成工作。** 每个归属日在日历／汇总显示一个“加班合计”，明细保留到达、离开、返回、用户确认、实际工作段、休息和未计入空档。当天返回继续加班会更新同一个日汇总，不创建两张彼此独立的加班汇总卡；内部仍保存多个真实 `segments`，不能压平成单一连续段。

例：原计划 18:00 下班，19:00 离开吃饭，19:40 返回并确认继续，21:00 离开。界面显示 **当日加班 2 小时 20 分钟**；明细显示 18:00–19:00、19:40–21:00，19:00–19:40 空档不计。不得为了“一条加班”算成 18:00–21:00 共 3 小时。用户明确标记为工作转场／连续工作的空档，才按其人工确认计入并标明来源。

计划结束前的临时外出继续按已确认规则不结束、不额外扣时；计划结束后的返回作为额外到访确认，但归并当天汇总。跨夜使用原班次锚点和现有记录时区，不按手机当前日历日拆成两笔，也不能把另一独立班次强绑进前一班次。

#### 缺失结束与异常

计划结束前离开后未返回，保存可供核对的下班候选，不自动认定提前下班；给至多一次核对机会，忽略维持既有规则。漏掉 EXIT、观察过旧、跨到下一班次或超过自动窗口时转待复核，不虚构结束、不无限把位置未知区间当作加班，也不截掉用户随后确认的真实长班次。

### 3.10 上班半小时询问、多地点与外勤／居家

#### 上班后 30 分钟，一班只问一次

`statusPromptAt = plannedStartAt + 30 分钟`。这是计划时间后的宽限，不是在收到某次晚到事件后再重新等待半小时；同一班次晚到、未到岗和状态未知合并成一次询问。用户未指定另一套晚到阈值，首版共用这条已确认的半小时规则。

| 到询问时的已知情况 | 处理 |
|---|---|
| 正常到岗、或用户已明确开始工作／确认今天继续记录 | 不再问“是否上班” |
| 晚于计划到达，但今日工作状态尚未明确确认 | 可问“已记录稍晚到达，今天按正常上班记录吗？”；不使用迟到责备或缺勤结论 |
| 新鲜位置表明不在任一工作地点 | 可问“今天开始上班了吗？”；不能由位置直接判断在工作或休息 |
| 没有到达事件／位置未知／旧位置 | 只说“尚未确认今天的上班状态”，不能说“确认你不在公司” |
| 已选外勤／出差／居家／休息，或全天请假 | 不按未到办公室继续催问；按对应状态及既有规则执行 |
| 仅因未批量复核而仍有 pending 建议 | 不单独触发“未到岗”；与物理到达／工作状态分开判断 |

进入 App 的两个主要选择是 **“今天休息”** 和 **“继续记录”**，并提供外勤／出差／居家和需要时的“确认开始工作”入口。“继续记录”只确认今日继续按现有规则记录、抑制本班次重复询问；不是同意应用所有自动化时间，不改循环模板、不回填到计划开始。

“今天休息”只覆盖对应班次锚点日；已有正式工作或自动采用结果时预览影响并保留历史，不静默删除。未回答／通知没送到，所有既有计时、排班、手动规则不变，不推断休息、缺勤、扣时或加班。

iOS 可预排中性询问并在得到执行机会时取消，不能承诺该分钟必定后台重新定位；晚到观测时间缺失或旧数据时不构造“刚迟到”的结论。严格新鲜位置条件可能少提醒，但不是用轮询／保活强行弥补的理由。[A3][A15]

#### 最多 5 个工作地点及转场

5 个地点共用现有排班／薪资，不并行开启多份收入；每地点稳定 ID、代次、名称、坐标、内外半径、启用状态，可选有效日期；第六个明确提示上限。临时工作地点也占名额。

统一聚合所有地点；已知在 B 内时 A 的 EXIT 不算离开全部工作区域，重叠区域不重复通知。双圈方案 5 地点共需 10 个条件，P0 校验系统额度与应用其他功能占用。

工作时段 A→B 转场沿用临时外出，不结束、不额外扣时。用户明确标记工作转场时，保持工作会话；计划结束后则需明确继续，未确认的空档不自动补成加班。不同地点／返回检测不能静默撤销已人工确认的结束，历史不确定空档仍供复核。

#### 外勤／出差／居家：今天或日期范围，不做家的地址

支持 `regular / fieldwork / businessTrip / remote / rest`，可选择今天或指定日期范围。范围按记录时区的班次锚点日解释；逐日人工修改优先，变更未来范围不覆盖已确认历史。

用户明确设置外勤／出差／居家后，继续使用原排班，不因未去普通办公室催问、不由普通办公室 EXIT 结束。工作起止由明确确认、外部动作或用户主动加入的临时工作地点提供。出差范围不等于连续工作整个范围，不从全天位置推断 24 小时工时。

**本轮决定不做家的地址功能**：不增加家庭地址字段、住宅围栏、离家开工／回家结束或第六类隐含地点；设置居家工作状态不要求填地址。用户自行把某个地址作为工作地点时仍受五地点和明确启用规则约束，不推断那是“家”。

### 3.11 可追溯记录与日历“认证”

每条最终记录至少可查：原计划、检测方式、系统观察时间（可能未知）、App 收到时间、规则版本与判定原因、应用时间与方式、之后每次人工修改／撤销。用户选择的“实际时间”不能覆盖原始触发时间；原始事件追加保留，但用户仍可删除自己的数据。

示例：系统观察到达 09:06、App 于 09:08 收到、用户周五 20:00 批量确认采用 09:06。记录来源仍是原生地理事件，采用方式为人工批量确认；不能把检测来源改成“手动”，也不能把上班时间改成周五 20:00。

日历名称已确认使用 **“定位认证”**。展开必须说明“设备位置证据支持所采用的上下班时间；不代表雇主审核、精确门禁时间或全天持续工作证明”。按边界显示上班认证／下班认证，只有一端时为部分认证，同一天汇总不抹掉其中未认证的段。位置质量规则需可解释，不用任意百分比分数。

| 情况 | 标识处理 |
|---|---|
| 有效原生边界、班次一致、时效明确且可用补充证据一致 | 可对对应已采用边界显示高质量位置标识；P0 验证证据可获取性和阈值 |
| 仅围栏回调、时效／补充信息不足 | 显示系统检测来源，按质量规则决定等级；不一律认证所有围栏事件 |
| 快捷动作声称由定位／Focus 触发 | 只标外部动作来源，不当作 DoneAt 已拿到定位证据 |
| 人工单条／批量采用，时间未改 | 保留原检测来源及其证据等级，另记采用方式；不能因人工采用就升级低质量证据 |
| 人工将 09:06 改成 09:00 | 09:06 原始事件保留，09:00 标手动调整；受改边界不继承不匹配的认证 |
| 仅一端有证据 | 标部分佐证，不能把整天所有工作段认证 |
| 待复核未应用 | 设置中显示参考证据；日历正式工时不得因另有参考就获得完整认证 |
| iCloud／备份恢复记录只有历史来源摘要 | 显示“定位认证 · 历史来源”，列出源方法与时间，不声称本机重新验证或防篡改 |

人工判断不是低价值数据，而是另一种来源。标识不能阻止用户改正定位错误。原始坐标、SSID、住址不需要为每个证据写进业务库；缺少精度／模拟标志时保留未知，不虚构测量。清除证据、冲突或改变已采用边界时重新计算标识。

### 3.12 设置中的单条与多选批量复核（已确认）

入口建议：**设置 → 自动化 → 自动化记录**。列表按班次／日期组织建议，展开后查看原始来源，而不是让用户在大量原生回调中逐条打勾。

| 列表信息／操作 | 契约 |
|---|---|
| 状态筛选 | 待复核、已自动应用、已人工确认、已忽略／已替代；不把未读等同未应用 |
| 记录摘要 | 日期／跨夜班次、计划起止、建议起止、建议加班、来源类型、证据状态 |
| 单条确认 | 支持采用完整建议或只采用上班／下班一端；可先修改建议再确认 |
| 多选 | 支持勾选多条及选择当前筛选结果；明确所选范围和数量，不能暗选筛选外记录 |
| 批量确认 | 一次预览所有选中记录的前后变化与工时／加班影响，点击一次“确认应用 N 条”，不再逐条重复弹窗 |
| 冲突记录 | 明显标记人工修改、多个候选、缺失边界或版本已变；不能擅自选择一条覆盖另一条 |
| 结果反馈 | 分别报告成功、已处理、需复核、失败；保留失败选择便于处理，不说部分成功为全部成功 |
| 后续更正 | 进入实际记录详情编辑／撤销；保留来源与应用链，不恢复整份旧快照 |

批量应用必须复用单条业务校验，不能直接遍历写 JSON。每批有稳定 batchID，每条有稳定 commandID／proposalID 和预期版本。对同一班次涉及多个边界的改变先形成一个一致的班次结果再原子提交；不同班次可以分别成功，并如实报告。

不能同时应用互斥的两条下班候选，不因为点击“全选”就默认取最晚一次；先选择有效候选或明确合并规则。缺一端的证据可仅更新该端，未得到确认的另一端仍按既有规则并清楚标明，不伪造已检测。负工时、跨班误绑定、乱序、旧地点代次等仍需校验。

人工批量确认保存 `originalSource`、`observedAt?`、`receivedAt`、`appliedAt`、`appliedBy=manualBatch`、`batchID`、修改前后值及规则版本。未经修改的检测时间可保留原证据；用户改过的时间标明“自动检测后手动调整”。重复点击、断网、杀进程／崩溃重试不重复应用，不重复增加加班。

自动应用开关开启后，旧待复核记录仍留在列表，由用户明确选择批量应用。关闭开关后保留已确认记录和历史溯源，不反向还原计划。

### 3.14 Plus、历史处理与系统入口权益

原生检测、自动化事件采集、自动应用和新自动化提醒归已有 Plus（月／年／终身）；不新增商品、不修改现有手工计时或 Watch 免费范围。拒绝定位、Siri 不可用或未订阅时，手工功能仍可正常使用。

实现必须分别检查 `canCollectAutomation`、`canAutoApplyAutomation`、`canReviewExistingAutomation`、`canCorrectExistingRecord`，名称可调整。新增自动采集／自动应用要求有效 Plus；试用是否有效遵循现有权益服务，不在本计划自创试用。

**历史处理保护作为实施默认**：到期不删除已产生参考／正式记录，不禁止对既有自动化建议复核、对既有自动修改更正／撤销；这是为避免数据无法纠错，不解锁所有历史统计或其他 Plus 功能。现有 `shouldCollectObservations` 若把上述操作一起禁掉，应在统一命令层显式调整并新增测试，不能靠 View 或 App Intent 绕开。

权益失效停止新监控／自动动作，取消尚未执行的自动开工／状态催问；不强行结束已开始的工作或清空实际记录。收到过期期间回调只记录必要的能力诊断，不积压一批日后偷偷自动应用的工作观测。用户恢复权益并再次启用时核对设备权限，不重放旧事件。

Siri／快捷指令可被系统发现不等于可执行所有付费动作。每次执行重新检查相同权益、文件保护和数据版本；不在后台弹购买页。只读查询复用当前免费／Plus 的既有可见范围，不把基础倒计时查询变成新的收费点；021 自动化操作仍是 Plus。复核与设置休息等影响记录的动作需明确确认，不能因系统推荐就越过用户授权。

## 4. iOS 实现

### I1 · App Intents 与快捷指令路线

**分开“记录自动化事件”与“用户明确操作”，禁止用同一不加区分的 Start Intent 绕过仅参考模式。** 首版对个人自动化提供“记录到达”“记录离开”；对用户操作提供“确认开始工作”“确认结束工作”和“打开自动化记录”。系统动作名可本地化，但语义必须明确。[A6][A7][A16]

- 自动化事件 Intent 不携带信任等级或 `isUserConfirmed=true` 参数，不把名字“到公司”视为定位认证；走相同留参考／自动应用／早到确认／去重规则。
- 显式确认开始／结束属于另一类命令，执行前由系统确认或打开 App 确认；无法确认时不能回落到静默修改。不能假设 App 能可靠区分同一个 Intent 来自 Siri 口令还是自动运行的快捷指令。
- 所有命令可在没有根 Scene／UI tick 的情况下保存必要状态。具体 `supportedModes`、`authenticationPolicy` 和前台跳转由 P0 按 deployment target 编译／锁屏真机验证，不降低整个业务文件保护。
- 引导到达／离开两条完整自动化，Focus 开／关作高级模板；手动切 Focus 也会触发，不把它认证为定位。App 提供动作及引导，不承诺公开 API 能静默替用户创建／读取／启用个人自动化。[A6][A8]
- Wi-Fi 触发以目标系统实际支持为准，不把断开指定 Wi-Fi 写成所有版本均支持；按版本验证指南。指南的“立即运行”“锁定时运行”等标签不能硬编码成全版本同一流程。[A7][A8]
- 仅快捷指令路线不导入地点、不启动定位会话或请求 DoneAt 定位授权；低权限不等于绕过系统自身的运行／认证限制。
- 关闭 DoneAt 外部自动化接收后，旧个人自动化调用返回明确未执行原因；用户需在系统自行停用，不能声称 DoneAt 已删除它。
- App Shortcuts／Siri 查询、捐赠、返回结果和隐私另见 I4；不会因打开 Siri 就再次写一条检测事实。

### I2 · 原生地理围栏

采用 `CLMonitor` 与 `CLMonitor.CircularGeographicCondition`。同名 Monitor 由一个应用级 owner 持有，统一注册最多 5 个工作地点的稳定内外圈标识、管理配额及聚合状态；事件消费者在启动恢复流程中重建，不放入 Widget／Watch Extension。[A1]

- 首先核对最低系统版本；不为本功能擅自抬升 deployment target。确实仍支持较旧系统时，用单独 adapter 处理旧 API，不能同时对同一地点启动两套监控。
- 对采用 iOS 18 及之后授权会话模型的路径，原生后台路线显式持有 `CLServiceSession(authorization: .always)`，按用户开启行为在前台建立授权目标，进程重建时及时恢复既有会话和事件迭代。仅保存“Always 已授权”的布尔值不足以代替生命周期管理。[A2]
- `unknown`、诊断错误和能力不可用不能映射为外圈离开。记录系统失败原因，向 UI 输出可用性状态。
- 以应用启动生命周期恢复服务，不能等用户进入设置页面才开始监听。注册与持久化配置做差异对账，重复冷启动不得重复注册／重复执行。
- 编辑地点／半径时递增 `registrationGeneration`，先停止接收旧规则的业务动作，再替换系统条件；旧事件不能命中新地点。
- “授权完成”“配置已保存”“围栏已注册”“已收到有效事件”是四个不同状态；设置页不可只凭开关为真显示“正常运行”。

### I3 · 权限与后台约束

- 用户主动点“使用当前位置”才请求前台定位；也应允许在具备选点能力时先选地点，再请求监控授权。
- 用户开启原生后台检测前，说明用途并逐步请求所需授权。相关 `Info.plist` purpose strings 与 19 语言说明一起交付。
- 首版办公楼小范围原生监控以满足精确定位要求作为能力门槛；授权／精度不足时显示“需完善权限”，保留快捷指令和人工入口。精度诊断与实际可用性由 P0 在目标版本验证，不能只把半径放大便承诺恢复。[A2]
- 使用一次性精确位置授权时不能把临时授权当成长期可用；前后台恢复都要重新核对授权、系统定位与会话诊断。
- `UIBackgroundModes` 只按实际使用的 Core Location API 配置。不能为保活滥加 audio、VoIP 或永久标准定位；需要 location mode 时在 PR 写明具体依赖与实测结果。[A3]
- 锁屏时验证业务文件保护与写入路径。业务数据不可访问时，最多保存当前保护策略允许的最小无坐标／无薪资命令信封，等待合法可用时复核；不能为自动化整体降低薪资数据库保护。
- 不承诺开机首次解锁前执行；不承诺用户划掉应用后继续原生监控；恢复后不凭旧状态补造整天记录。[A3]
- 早到、非工作时段、上班后 30 分钟提醒按 §3.8–§3.10 预排、取消、去重。早到询问不早于计划开始则不预排；已过期询问不补发。接受询问型而非已核验型文案，本地通知不等于后台代码执行机会。
- 后台启动实时活动不是本功能成功标准。可更新／结束已有活动时复用现有服务，创建新活动受系统规则限制时退回通知与 App 内状态；不得为创建活动主动弹出 App。
- iPad／在 Mac 上运行的 iOS App 不因共用代码自动成为执行设备；首版围绕随身 iPhone 验收，其余设备保留手动操作与能力说明。

### I4 · Siri、App Shortcuts 与系统建议

#### 能力结论与边界

可以接入，分为**可主动调用的动作／查询**、**系统自行决定是否展示的建议**、**执行后的信息返回**三个层次。App Shortcuts 让核心动作出现在 Siri、Spotlight、快捷指令等系统入口；Intent 结果可包含可朗读的对话和可视结果卡片。[A16][A17]

`IntentDonationManager` 用于将已完成的真实用户交互提供给系统，`PredictableIntent` 用于描述可预测动作及其展示，帮助系统根据使用行为建议重复动作。[A18][A19] 接口调用成功只代表提交成功，不证明已获得 Siri 建议曝光；系统位置判断、位置权限、主动到离岗推送仍走原路径。

这些是**DoneAt 向系统提供能力／有限上下文**，不是从 Siri 读取用户“常去公司”“家的地址”或系统推断的真实上下班历史。不能从建议出现／被点过反推用户真的到了公司。系统级语音处理与建议属于 Apple 能力，隐私文案不得宣称 Siri 的处理都只在 DoneAt 内完成。

#### 首批拟提供的六个入口（名称与短语需目标语言真机验证）

| 拟新增 Intent | 对用户的能力 | 结果／确认要求 |
|---|---|---|
| `GetWorkdayStatusIntent` | “用 DoneAt 查看今天班次” | 返回计划开始／结束、当前状态、已确认／估算／待复核标识；不返回薪资 |
| `GetClockOffCountdownIntent` | “问 DoneAt 还有多久下班” | 复用既有规则返回剩余有效工作时间；休息、跨夜、已到计划结束需准确区分 |
| `OpenAutomationReviewIntent` | “打开 DoneAt 待复核记录” | 先返回待复核数量的最小摘要，安全地打开复核页；不在建议里展示整份历史 |
| `ConfirmWorkStartIntent` | “用 DoneAt 确认开始工作” | 展示／朗读要采用的班次和时间并明确确认；不能仅因系统建议出现而开始 |
| `ConfirmWorkEndIntent` | “用 DoneAt 确认结束工作” | 显示所影响班次及本次结束时间，经确认走统一命令；存在冲突则打开 App |
| `ConfirmRestDayIntent` | “在 DoneAt 把今天设为休息” | 明确确认锚点日及已有工时影响，必要时前台预览；不能静默删工作 |

上表是新增实现计划，不是仓库已有类型；查询可组合成带参数的动作以保持入口克制。语音短语带应用名，不能保证无应用名的“我下班了”由 DoneAt 独占，也不承诺自定义意图在所有 Siri 语言／机型／系统上同等理解。

自动化中的“记录到达／离开”继续由 I1 提供，不以这两个确认命令替代。新增确认动作被快捷指令复用时，也必须经过真实确认，不信任调用者传来的来源字符串或自称已确认参数。

#### 系统建议与最小捐赠

- 首版通过一个 `AppShortcutsProvider` 暴露少量关键入口。用户主动且成功完成开始／结束／查看复核等操作后，才按当前 App Intents API 捐赠对应的可重复动作。[A18][A20]
- 不在每次定位 ENTER、后台自动应用、每秒倒计时、通知展示或跨设备同步时捐赠；它们不是用户刚主动做的交互。批量确认不向系统捐赠几十个历史上下班动作，最多表达一次“查看／复核记录”的真实操作。
- 捐赠内容仅含必要动作类型和去敏语义；不含坐标、公司名称、SSID、薪资、原始事件日志或完整工作史。不要让日期型历史参数把“下次开始工作”固定为上周一；默认查询当前班次，执行时解析最新值。
- 保存本机 donation ID 与对应业务动作，以便用户撤销、删除相关数据或关闭本 App 的建议捐赠时调用删除接口；删除捐赠不等于能保证立即清除系统所有展示／学习结果。避免和系统自动产生的交互重复捐赠。[A18]
- `PredictableIntent` 的描述与枚举参数只表达有效操作，不通过假捐赠、定时捐赠或高频更新操纵推荐。禁止重复创建相同动作以争取更多系统位置。
- 提供“向系统提供操作建议”开关；实现默认首次使用对应系统能力时解释并由用户开启，拒绝不影响定位／通知／记录。此开关控制 DoneAt 主动提交的捐赠，不声称能够关闭系统全部学习／自动交互记录；系统侧控制遵循其设置。用户关闭系统 Siri／搜索／学习相关选项后不显示“服务故障”。

#### 带出信息：返回值、对话与卡片

首版返回仅包含必要无薪资字段的 `WorkdayStatusProjection`：锚点日、计划下班、状态、剩余有效时间、已采用加班、估算加班、待复核数量、数据更新时间。按授权和保护状态裁剪；原生定位认证详情留在 App 内，不把底层位置证据塞给 Siri。

`ReturnsValue`／`ProvidesDialog` 支持快捷指令继续使用结果以及 Siri 语音反馈；可视卡片使用目标 SDK 支持的 snippet 返回机制。[A17][A21] 当前已发布系统支持的交互式 snippets 可作为第二批增强，用于查看摘要和进入复核；旧系统退回对话与打开 App，不能为了卡片抬升最低系统版本。[A22]

所有金额继续遵守仓库既有保护。锁屏时按 App Intent 认证策略及设备文件保护校验，不可读就中性提示需解锁，不能将工资数据库全部降级为锁屏可读。Siri 读出“预计加班”不能被用户误解成“已记入工时”；读取本身不得更改上班状态、产生定位事件或执行同步回放。

**不把批量确认放在零预览的语音动作里。** 首批 Siri 只打开复核；多条更改仍在 App 预览后一次确认。单次修改的系统确认、取消、重复执行、旧参数和冲突均通过业务命令层处理。

#### 现有小组件与后续系统能力

可以在既有 Widget 的无薪资 timeline 上评估相关性信息，帮助系统选择在合适时候展示小组件；Smart Stack 仍由系统和用户设置决定，不是强制弹出卡片。[A23] 只读 Watch 范围不变，不借 Siri 需求偷加 Watch 控制或新定位服务。

公开新材料中的 `RelevantEntities`、`SyncableEntity` 等仅作为后续 P0 检查项；必须核对实际 SDK availability、系统版本、匹配的 schema 和隐私用途后才能纳入。不能把资料标题年份当成最低可用系统版本，不为获取系统展示而套用不匹配的 app schema。[A24] 新 API 缺失不阻塞基础 App Shortcuts、查询与合规捐赠路线。

#### 接入与验证输出

应用级统一 provider、无 Scene 可初始化的只读查询服务、具备明确确认策略的写命令 adapter，以及捐赠／撤回管理器；不在 Siri 层新建排班或薪资算法。中文／英文短语、其余 19 语言资源、当前与最低支持系统、锁屏／解锁、冷启动、Plus 到期、Siri 关闭、结果时效和无网络均实测。报告分别记“动作可发现”“查询／执行通过”“捐赠调用成功”“实际观察到建议”，最后一项未出现不能冒充通过或必达。

### 拟涉及路径

现有复用：`src-mobile/ios/App/App/Native/Models/ShiftSessionStore.swift`、`ShiftSession.swift`、记录命令队列、权限与提醒服务，以及 `Localizable.xcstrings`。

拟新增：`Native/Models/WorkplaceAutomationRules.swift`、`Native/Services/WorkplaceAutomationCoordinator.swift`、`Native/Services/WorkplaceMonitorService.swift`、`Native/Services/WorkplaceAutomationStore.swift`、应用级 `DoneAtAppShortcutsProvider`、只读 `WorkdayStatusProjection`、App Intents 动作／捐赠 adapter 及 `Native/Views/` 设置页面。CloudKit／RecordJSON 只扩展现有统一业务同步路径。名称可按工程模块收敛，不为每个状态拆出无必要的层。

`Native` 与 `AppTests` 已为 synchronized folders；新增 Swift 文件按现有工程规则编译，不手工添加重复 PBX 条目。权限资源、其他目录及共享源文件按 iOS 规范检查 target membership。[R2]

## 5. Android 实现

### A1 · 领域层与 GMS 适配器

- `:core:domain` 增加纯 Kotlin 自动化规则、事件模型和状态转换，所有当前时间／时区均显式注入；不得引入 `android.*`、Google Play services、Room 或隐藏的 `Instant.now()`。
- `:app` 负责权限、系统事件、GMS 能力检测和 UI；`:core:data` 负责最小本地自动化存储及可恢复命令处理，沿用项目原子 JSON 写入边界。[R3]
- 使用 `GeofencingClient` 为最多 5 地点注册内外圈并统一聚合，稳定 request ID 绑定地点与配置代次；原生停留增强使用 `GEOFENCE_TRANSITION_DWELL`／loitering delay，而非后台定时轮询。[A4][A5]
- 使用显式目标的 `PendingIntent` 指向内部 Receiver。按目标 SDK 设置更新标志；Geofencing 要求可变 PendingIntent，Android 12（S）及之后显式使用 `FLAG_MUTABLE`，并保持显式组件目标与 Receiver 的最小暴露范围，不能照搬其他提醒的 immutable 配置。[A4][A5]
- Receiver 保持最小职责：解析、校验、持久化最小事件并提交可恢复处理；不弹 Activity、不在 `onReceive` 内执行长时间定位或等待。
- 早到、非工作时段 DWELL 与正常到岗候选按到访／班次区分，早到等待跨入计划开始则不额外询问；同一事件不能既自动上班又邀请加班。上班状态统一在计划开始后 30 分钟、每班一次；后台调度允许延迟，不用精确闹钟或常驻服务凑准点。确认开工、跨段合并及批量应用均调用统一业务命令。
- 首次注册、重建后的初始事件与真实边界变化分开；不能无条件使用 `INITIAL_TRIGGER_ENTER` 导致每次重建都自动上班。
- 设备重启后按仍有效的本地授权重新注册；`GEOFENCE_NOT_AVAILABLE`、注册失败、GMS 数据变化、应用更新后及返回前台时做修复对账。重装／清除数据后没有原配置时，不凭空恢复启用。[A4]
- 数据尚不可用、强行停止后首次重开或系统能力被关闭时执行恢复检查，不能把“Receiver 已声明”当成可用证明。

### A2 · 权限、系统设置和不可用设备

- 使用原生后台围栏需要对应精确位置和后台位置授权；Android 11 及之后的后台授权通过系统设置流程处理，不把前台和后台请求无差别塞进同一弹窗。[A4][A9]
- 按 target SDK 正确处理 coarse／fine 组合请求及精确选择。后台权限已授予但仅近似位置，不得显示办公楼级监控已就绪。[A9]
- 系统定位、GMS 可用性／版本、注册结果与通知权限分别展示。通知被拒绝不等于定位无权运行，也不得阻断人工使用。
- 不可用 Google Play services 的设备返回 `unsupported`，保留人工班次、小组件等既有能力；不给死循环重试或“开启某个权限即可修复”的错误提示。
- 首版不自动引入其他地图／定位厂商 SDK。非 GMS 适配作为单独 provider、独立隐私披露和实测范围，不能用持续 GPS 或任意轮询冒充同等替代。
- 不用定位前台服务长期驻留，不要求精确闹钟权限执行围栏防抖，不滥用忽略电池优化豁免。厂商省电说明作为诊断辅助，不保证放宽限制后必定成功。
- 本地恢复检查若使用 WorkManager，必须承认其调度可能延迟；结束是否生效仍由当前业务证据判断，不按 Worker 跑到的时间倒推离开。

### A3 · 备份、组件与发布隔离

- 新自动化配置、注册凭据、候选事件和处理队列进入专用本地目录／`noBackupFilesDir`，不得放入会被备份的 `device/settings.json` 或 `syncedPreferences`。
- 同步／恢复业务归档时保留正式记录的最小来源摘要，不恢复设备授权、原始定位日志或自动化开关；导入来源显示历史认证。归档写入仍受现有损坏隔离、编码回读与版本检查约束；Android 不因此新增 iCloud 服务。[R3]
- 小组件只接收现有无薪资投影，不启动围栏或生成独立班次；后台完成业务事务后用既有更新通道刷新。
- 后台定位模块与权限应支持编译期排除。未决定提交原生定位功能的发布产物，merged manifest 中不得仅凭隐藏开关继续保留后台位置权限。
- Google Play 的权限审查是单独发布门禁，不把审核风险拖进已批准的 Android 基础移植范围；未获准时可以交付不含该模块／权限的基础版本，不能暗中保留未披露能力。[A10]

## 6. UI、本地化与隐私审核

### UI 与可诊断性

设置页面围绕用户任务组织：Plus 自动化说明、检测方式、最多 5 地点、自动应用时间开关、自动化记录／批量复核、30 分钟状态询问及停留通知、今日／范围工作状态、可用性、暂停／删除；iOS 增加 Siri／系统操作建议引导。没有家的地址入口。地图不是首页主视觉，技术诊断放次级区域。

- “地点已保存”与“正在自动检测”分开；GPS／权限／GMS 不可用时给出一条真实可执行的下一步。
- 先复用工程已有选点能力；如 Android 尚无合适地图组件，首版可先提供“使用当前位置”与必要的高级修正，地图搜索另立依赖。不得无说明增加付费服务、API key、遥测 SDK 或账号要求。
- 定位、选点、地图展示的坐标系统保持一致；不同供应商混用时显式记录转换边界并实地核验，不手工猜偏移，不能只在模拟器上证明公司地址正确。
- 未开启自动应用时仅记录待复核，不弹首次强制二选一；设置记录页支持多选批量确认，显示计划／建议／实际、来源及证据。日历标识跟随真正采用的边界，不认证未应用参考。
- 显示最近已知能力和事件，不制造实时在线心跳；“长时间未收到事件”不自动等于异常。首页已到计划结束时显示等待离开与可选估算；日历加班按日一条总计、详情保留真实段与空档，认证按边界展示。
- 通知提供“查看记录”“撤销本次”或进入 App 确认的入口；撤销必须遵循版本校验。所有通知与分享保持无薪资、无精确地点。
- 完整覆盖浅色／深色、辅助字号、屏幕阅读器、长文案、RTL、横竖屏与平板。iOS 视觉测试仍遵守明确授权规则，代码完成不等于已做真机视觉验收。

### 本地化

iOS 新文案进入 `src-mobile/ios/App/App/Localizable.xcstrings`，覆盖现有 19 个 UI locale；Android 共用文案经 `generate:android-strings` 生成，Android 专属权限／GMS 提示进入 `app/i18n/android-strings.json`。不得直接编辑生成资源，不把 iOS 专属文案重新塞回 Web 的所有 locale。[R1][R3]

权限 purpose strings、快捷动作名称／短语／描述、Siri 对话与结果卡片、“定位认证”完整／部分／历史标识、通知、未执行原因和设置帮助均覆盖 19 语言。系统设置标签优先使用平台提供的本地化名称，不将中文“始终允许”拼进所有语言。Siri 语言覆盖与 App UI 19 语言覆盖分别验收，不保证系统语音支持同样的语言集合。

建议文案，实施时以实际行为校对：

> **工作地点自动化**  
> 到达或离开工作地点时提醒你，检测时间默认留作参考。你可以开启自动应用，或复核后一次确认多条。同一天的加班合并展示，实际到离岗过程保留。系统识别可能有延迟，记录可以随时修改。此功能包含在 DoneAt Plus 中。

> **原生定位说明**  
> 开启后，DoneAt 会在你未使用 App 时访问位置，用于判断是否进入或离开设定的工作区域。不保存连续位置轨迹，地点坐标留在本机。已采用的工时及最小来源记录，可随你开启的私人 iCloud 同步或备份保留；原始定位日志不随之上传。你可以随时关闭检测。

> **快捷指令方式**  
> 由 iPhone 的快捷指令触发班次操作，无需向 DoneAt 授予定位权限。请按当前系统的提示设置自动运行与锁定时运行。

### 隐私、数据格式与商店审核

- 不为本功能新增广告、分析、登录、雇主端或员工监控服务器。系统位置服务和地图供应商的数据行为需如实说明，不能泛称“所有数据绝不离开设备”。
- 本机位置处理不自动等于 App Store 标签中的“收集”，但使用定位也不自动证明可维持 `Data Not Collected`；需要核查业务记录同步、SDK、日志和诊断的实际数据流。[A11]
- 最小来源摘要已获准按 §3.7 进入正式业务备份／私人 iCloud 同步。先审计 `RecordJSON`、CloudKit 当前协议与旧版读取／回写行为，必要时正式版本迁移、跨端导入和云合并测试；不能把不兼容结构继续标为现有 v6，不用新客户端能导入来代替旧客户端安全性证明。[R3]
- Apple 提审材料解释位置与班次功能的关联、授权路径、关闭方式和审核人员可复现步骤；遵守后台用途与位置使用要求，不给通过率或“比 Android 更容易”承诺。[A12]
- Google Play 提交显著披露、隐私政策、后台位置权限声明和真实 Android 功能演示。其政策对核心用途和必要性有要求；“方便自动记录”并不意味着必定获批。[A10]
- 审核演示应显示实际 App 的开启、授权与后台生效过程。可以压缩演示时间，但不得用调试注入假装真实后台定位。
- 不写入未经重新核对的未来政策生效日期。发布前再核对官方要求与 merged manifest／最终 archive，不能只检查 Debug 配置。
- 自动化已确认纳入现有 Plus，不新增 SKU，不改变月／年／终身商品及价格。到期后停止新自动化但保留历史复核／纠错保护；语音、通知 action、后台回调、导入路径不能绕过统一权益，见 §3.14。
- Siri／系统建议属于新的系统交互出口，只提供去敏操作／最小只读结果；单独说明其用途、关闭／撤回方式，不把用户批准 iCloud 同步等同于批准向 Siri 提供完整历史。

| B43 | 从 A 离开但已知仍在 B 内 | 不结束班次、不重复发整班离开通知；不误触发半小时未到岗询问 |
| B44 | A→B 转场、外勤与普通模式 | 正常工作时段保持同班；计划结束后需明确继续，未知空档不补加班，不撤销人工结束 |
| B45 | 居家／出差状态，无家的地址功能 | 不存在住宅字段或离家／回家计时；范围状态只影响相应班次，不生成连续 24h 工时、不反复未到岗询问 |
| B46 | 手动批量采用高质量未修改时间 | 保留检测来源与边界证据；采用方式另记，不提高原质量等级 |
| B47 | 只有一端证据／证据未应用／之后手改 | 标部分、参考或手动调整，不给整天完整认证 |
| B48 | 清除短期诊断、删除地点 | 正式记录最小溯源不丢；主动删除证据后标识降级 |
| B49 | 通知已过期或用户已处理后点开 | 重读最新版本，不按旧通知自动覆盖 |
| B50 | 关闭自动应用时已有待执行自动写入 | 提交前重检开关，转待复核；不继续执行旧自动策略 |
| B51 | 09:00 上班、08:20 到、默认等待 30 分钟 | 保存到达，08:50 可问早到；未确认不增加计划前工时 |
| B52 | 09:00 上班、08:50 到、默认等待 30 分钟 | 不安排 09:20 早到询问；按掐点只记，不自动增加 10 分钟提前加班 |
| B53 | 08:30 到、询问目标恰为 09:00 上班 | `dueAt == plannedStartAt` 也抑制早到询问，不依赖 09:00 后台取消 |
| B54 | 早到用户在询问前明确开工或离开 | 取消／失效原询问，同访不再重复邀请加班；旧通知点击重校验 |
| B55 | 早到只确认到公司／早餐，而未确认开始工作 | 不生成提前加班，不把“到了”混同“工作了” |
| B56 | 09:00 上班、09:20 晚到但尚未确认今日状态 | 09:30 中性询问最多一次；不是 09:50 再问；时间采用依旧服从总开关 |
| B57 | 09:30 未到岗已询问、09:50 才检测到达 | 更新已有询问状态，不再等半小时第二次追问；不虚构 09:00 开工 |
| B58 | “继续记录”且自动应用关闭 | 今日状态确认、停止重复问；参考仍 pending，不批量应用、不改模板 |
| B59 | 正常已到岗但 N 条参考尚未复核 | 不因未复核再问未到岗；只读查询正确返回待复核数 |
| B60 | 休息日 14:00 到、14:30 明确开始加班 | 默认从 14:00 计，不扣掉前 30 分钟；保存检测／提醒／确认三个时刻 |
| B61 | 用户确认额外加班时已离开 | 补记相应已结束段，不启动进行中会话；缺边界进入核对 |
| B62 | 计划 18:00，19:00 离、19:40 回且确认、21:00 离 | 一条当日加班汇总 2h20；详情保留两段与 40 分钟非工作空档，不算成 3h |
| B63 | 同日提前、延续和返回加班段重叠 | 按并集去重合计一个当日汇总，原始证据各自可追溯 |
| B64 | 计划已结束但没有 EXIT | 倒计时结束、等待记录；估算明确标注，不能进入已确认汇总或自动认证 |
| B65 | 17:30 提前离开、18:00 没返回 | 保留 17:30 候选并可问一次；不自动倒推下班或删除后续人工工时 |
| B66 | 出差日期范围内存在某天人工设休息 | 当天人工优先，其余日期按范围；不改过去确认记录 |
| B67 | iCloud 恢复含最小来源的正式记录 | 时间／修改链保留、显示历史定位认证；不恢复围栏、再发通知或自动执行 |
| B68 | iCloud 多端人工修改和自动结果并发 | 走现有冲突解析、稳定 ID／版本；不得源端／目标端各增加一次工时 |
| B69 | iCloud 删除、离线重试、账户切换 | 墓碑传播且不复活已删除证据；不把旧账户载荷传给新账户 |
| B70 | 第 89 天参考、清理第 7 天诊断 | 参考详情仍能解释；第 90 天规则明确，已采用来源不随清理丢失 |
| B71 | Plus 失效时正在工作 | 停新自动采集／应用，不强制下班；允许处理此前记录，不解锁其他 Plus 统计 |
| B72 | 旧客户端读取新来源结构再回写 | 通过版本门禁／兼容策略防止无声丢失来源；跨端导入不伪认证 |
| B73 | 系统观察时间缺失／通知迟到至计划开始之后 | 不用收到时间伪造迟到／早到；不补发已失效早到询问 |
| B74 | 同日一段认证、一段人工补记 | 汇总仍一条加班，认证按边界／段部分显示，不能认证整日 |



### 8.2 平台与设备用例

- [ ] iOS：前台、后台、长时间锁屏、系统回收后恢复、用户划掉后再次打开、重启后首次解锁、后台刷新设置变化、全局定位关闭、Always 降为 When In Use、精确位置撤销、监控注册失败分别记录结果。
- [ ] iOS：快捷指令到达／离开、Focus 开关、锁屏执行、系统不允许自动运行、个人自动化被停用、重复执行与无可见 Scene 均验证。DoneAt 不请求定位的路线有证据。
- [ ] Android：受支持 API 的权限组合、GMS 正常／缺失／禁用、后台与 Doze、省电、强行停止、划掉任务、重启、应用升级、数据清除和注册不可用分别验证；不把划掉任务等同强行停止。
- [ ] Android：至少一台标准 GMS 设备及一台具有额外后台策略的目标厂商设备完成测试；不能用单一模拟器结果宣称覆盖所有厂商。
- [ ] 双端：无网络、Wi-Fi 关闭、网络弱、手机静止、室内外切换时只报告实测能力，不宣称围栏完全离线可靠。
- [ ] 通知权限拒绝时，记录／应用按设置仍正确；通知允许时到离岗去重、不泄露薪资或具体地点；验证预排询问的取消竞态与点击后版本检查。
- [ ] 双端：多选／全选当前筛选范围、批量预览、部分失败、重试、旧建议与同班次候选冲突完成真实界面及持久化测试；5 地点聚合／配额失败有设备证据。
- [ ] Widget／Watch／实时活动保持既有信息边界；后台无法新建实时活动不影响业务命令成功，但 UI 不误报已开启。
- [ ] 备份／导出／私人 CloudKit 实际载荷检查：正式记录及最小来源可同步，坐标、SSID、围栏 ID、原始日志、待执行队列和设备启用状态不混入；恢复不触发动作／通知／捐赠。
- [ ] 双端验证早到 08:20／08:30／08:50 对 09:00 的边界、09:30 晚到／未确认询问、跨夜计划、非工作到访 30 分钟提示延迟及取消竞态。
- [ ] iCloud 真机双设备验证最小来源同步、离线合并、历史认证、账户切换、删证据降级及旧客户端兼容；未开启云同步不产生这类云端载荷。

真机试点建议覆盖至少 10 个完整到离岗周期，包含午间外出、路过、弱网络和冷启动；记录样本量、触发成功／漏触发、误开始／误结束、系统观察到执行的延迟及人工修正次数。小样本只作试点结果，不据此宣传百分比可靠性或固定电量消耗。

单独做启用／关闭对照电量测试，记录设备、系统、时长、移动条件和后台行为。不得用“没有持续 GPS”直接推导“零耗电”。默认模式若出现无法解释的午间误结束、重复记录或人工修改被覆盖，阻断发布，而不是修改测试预期。

### 8.3 Siri／系统建议验收

| 编号 | 场景 | 必须满足 |
|---|---|---|
| S01 | App Shortcuts 安装后被系统发现 | provider／元数据与本地化完整；未触发业务写入，不等于已有个人自动化 |
| S02 | 查询今天状态／还有多久下班 | 复用统一规则，与 App 同时刻一致；无薪资、坐标、SSID，跨夜正确 |
| S03 | 计划结束但等待离开／仅参考 | Siri 清楚区分计划、估算、已采用与待复核，不读成认证实绩 |
| S04 | 外部“记录到达”动作且开关关闭 | 只记参考，无定位权限依赖，不因 Siri／快捷指令入口自动应用 |
| S05 | 确认开始／结束意图由自动快捷指令调用 | 仍需显式确认；无交互能力时不静默写入，不信任伪造已确认参数 |
| S06 | 用户取消确认／误触建议 | 无业务写入、不生成假检测、不捐赠为已完成工作 |
| S07 | 明确确认、并发重复执行、旧班次参数 | 一次提交；重读版本／shiftKey，旧结束不结束新班 |
| S08 | Siri 设置今天休息且已有实际记录 | 明确预览／确认，不静默清空；必要时安全打开 App |
| S09 | 冷启动／锁屏／文件保护／Plus 过期 | 一致授权与权益，不能降级数据库保护或偷偷弹购买 UI |
| S10 | 捐赠动作、自动采用、批量历史确认、云回放 | 仅适宜的已完成用户交互捐赠；不高频、不为历史每条刷捐赠 |
| S11 | 撤销／删数据／关闭操作建议 | 调用合适的 donation 删除；如实记录结果，不保证系统立即清空学习 |
| S12 | 捐赠调用成功但看不到系统建议 | 分开报告“已提交”与“观察到展示”，不说必定曝光或伪造截图 |
| S13 | Siri／搜索建议被系统关闭 | 自动化主功能仍工作；不报定位异常，不引导危险绕过 |
| S14 | 当前系统结果卡片、旧系统仅对话 | 无崩溃、无最低版本抬升；结果刷新／引用版本正确 |
| S15 | 中文／英文／其他本地化与 Siri 语言组合 | 原生资源 19 语言完备，实际语音支持单独记证据，不以 UI 翻译等同 Siri 支持 |
| S16 | 主动打开复核／批量修改 | 进入 App 预览后明确确认；不能用一句语音未经预览应用全部积压记录 |
| S17 | 运行来源无法区分 Siri 与 Shortcuts | 来源记 App Intent／未知，不伪造“用户语音确认”或定位认证 |
| S18 | Smart Stack／Watch 相关性增强 | 不改变 Watch 只读范围、无薪资投影；系统未推荐不影响业务完成 |

以上是待执行规格，不是通过数量。Siri 自定义短语识别、受保护文件和建议实际展示均要真机证据；单元测试只能证明规则，不能证明系统会推荐。

### 8.4 自动化、构建与文档门禁

- [ ] Swift 与 Kotlin 自动化规则使用同一组显式时间／时区事件 fixture；核心状态转换、命令结果、去重与撤销逐项对齐。
- [ ] 修改共有排班／收入规则时，更新对应 TS／Swift／Kotlin 与既有 fixture；只增加平台自动化规则时不把平台 API 塞入共享公式。
- [ ] iOS 全量相关测试与性能测试串行执行，确认实际用例数；不得因过滤器未命中而把“0 tests”写成通过。[R2]
- [ ] Android 每个相关模块测试、Lint 与 Debug／Release 构建通过；最终 merged manifest 与权限清单单独检查。[R3]
- [ ] 19 语言、占位符、复数与生成资源检查通过；视觉检查有真实执行记录，未做则明确写未做。
- [ ] 新增的数据格式、恢复命令和备份排除有回归测试；现有 Widget、Watch、提醒、Focus、收入与人工记录不回归。
- [ ] 官方权限与审核要求在提审前重新核对；能力说明与实际二进制一致，发布须另行授权。

按变更范围执行工程现有命令，不擅自更名或降低门禁：

```bash
# 仓库根目录；以下生成脚本仅在对应输入有变更时执行。
# 本地化有变更时：
npm run generate:android-strings

npm run generate:ios-rule-fixtures

npm run lint
npm test
npm run check:ios
npm run check:ios-strings
npm run check:version

# iOS：先确认本机可用 destination；示例名称来自现有工程规范。
xcodebuild -project src-mobile/ios/App/App.xcodeproj -scheme App \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' build
```
